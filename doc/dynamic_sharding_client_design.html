Goblin Dynamic Sharding — Client-Side Logic Design

How the Goblin client routes keys correctly during an online shard migration, driven entirely by the Object Store's response codes. The companion to the server-side v2 Target Design.

TL;DR The one-RouteInfo problem Response-code contract Client state Routing decision Retry loop ASK redirect MOVED refresh Edge cases Code gaps Work plan

TL;DR

A Goblin client caches exactly one versioned RouteInfo (shard→cluster map + routeVersion) and stamps that version on every request. The server's preExecute compares the stamped version against its own and, together with per-shard migration state, replies with one of four route response codes. The client never tries to predict migration; it reacts to those codes. This document specifies that reaction for each code so that reads and writes stay correct while a shard moves from a source cluster to a target cluster.

The two redirect primitives mirror Redis Cluster, exactly matching the server design:

  • ASK MIGRATED_ROUTE (451) — per-key, transient. "This one key already moved; ask the target this once." The cached route is not changed.
  • MOVED CLIENT_ROUTE_OUT_OF_DATE (452) — stable. "Your map is stale; refresh RouteInfo from the OM and retry." The shard's owner has flipped.

The "client holds only one RouteInfo" problem

Today the client keeps a single RouteResult inside ShardingInfo and resolves every key through it: hash(key) % (1<<shardFactor) → shardId → the one cluster that currently owns that shard. There is no notion of "old map" vs "new map" — the client either has the pre-migration map or the post-migration map, never both at once.

ShardingInfo.java:21 (single volatile RouteResult), :84-103 (getShardingClient), :49-76 (refreshClientMap monotonic by version)

During a migration the key space is momentarily inconsistent with any single snapshot: a shard S is half-moved — some of its keys still live on the source, the rest already on the target. No single shard→cluster map can express "this key is on A but that key is on B for the same shard." So which map should the client hold?

The resolution: anchor to the source, let the server redirect per key. The client keeps the pre-migration map for the whole of Phase A. It always sends a migrating shard's keys to the source. The source answers authoritatively per key:
  • key still present → serve it normally;
  • key already exported → MIGRATED_ROUTE with the target address → the client retries that single key on the target (ASK), without mutating its cached map.
Only when the server commits the shard to its new owner (Phase B) and bumps routeVersion does the client swap to the new map — lazily, on the next CLIENT_ROUTE_OUT_OF_DATE. This way one RouteInfo is sufficient and correct; the per-key gap is filled by the transient ASK redirect, not by a second map.

This is only safe because the server runs a two-phase route: ownership of a migrating shard stays on the source until migration of that shard finishes. If the OM flipped ownership the instant the ring is recomputed, the client's single map would point at a target that has no data yet. The client design below assumes the server honours that contract (server design §1, "Two-phase route, Redis-style").

The response-code contract

Every Object Store reply carries a ResponseCode. The client maps each code to exactly one action. Codes are defined in protocols/common.proto:15-33; the client dispatch table lives in RaftClusterClient.java:230-245 and the action bodies in RaftClusterClient.java:385-412.

The version stamp is what makes 452/453 possible. The client must put its cached routeVersion on every Object Store request header. The server's preExecute compares header.routeversion() with its own and returns 452 (client behind) or 453 (server behind). If the client ever forgets to stamp, or stamps a stale value for a redirected request, the staleness handshake breaks. server preExecute: ObjectStore.cpp:119-128; client stamp: StoreClusterClientImpl.updateRouteVersion :33-37, ShardingInfo getShardingClient :96-99.

Routing decision for a key

getShardingClient(key) resolves a key to a cluster client under the read lock:

shardId  = key startsWith "/RMSTRX"  ?  RMSTRX_SHARD_IDX
                                     :  hash(key) % (1 << routeInfo.shardFactor)
cluster  = the ShardCluster whose shardInfo set contains shardId
client   = clientMap[cluster.address]
client.updateRouteVersion(routeInfo.routeVersion)   // stamp the version we are routing against
return client

ShardingInfo.java:84-103. The shardFactor (12 ⇒ 4096 shards) and the per-shard ownership both come from the OM's RouteInfo, so the client never hardcodes placement.

Invariant. The version stamped on a request must be the version of the map used to pick the cluster. A redirect client (ASK target) is an exception — see §ASK for the version it must carry.

The execute / retry loop

All single-key operations funnel through ShardingClientImpl.execute(request, key, caller), a loop that re-resolves and retries on routing exceptions and returns on success. Each routing code surfaces as a typed exception from RaftClusterClient, which the loop catches.

ShardingClientImpl.java:271-298 (loop); exceptions in com.ebay.payments.raft.client.exceptions.

Today

while (true) {
  try {
    if (client == null)
      client = getShardingClient(key);
    return caller.call(req, client);

  } catch (RouteOutOfDate e) {        // 452
    refreshClientMap(om.route());
    client = getShardingClient(key);

  } catch (MigratedRoute e) {         // 451
    client = getRedirectClient(
               e.getRedirectAddress());

  } catch (WrongRoute e) {            // 450
    throw new GoblinInternalException(e); // FATAL
  } catch ( ... ) { throw ...; }
}

453 is absorbed inside RaftClusterClient as a same-address retry, so the loop never sees it. RaftClusterClient.java:410-413.

Target (this design)

attempts = 0
while (true) {
  try {
    if (client == null)
      client = getShardingClient(key);
    return caller.call(req, client);

  } catch (RouteOutOfDate e) {        // 452 MOVED
    refreshClientMap(om.route());
    client = getShardingClient(key);

  } catch (MigratedRoute e) {         // 451 ASK
    client = getRedirectClient(
               e.getRedirectAddress());
    // one-shot: next failure re-resolves

  } catch (WrongRoute e) {            // 450
    refreshClientMap(om.route());     // FIX: refresh+retry
    client = getShardingClient(key);

  } finally bound(++attempts);        // cap + backoff
}

Two behavioural fixes: WRONG_ROUTE becomes a refresh-and-retry instead of fatal, and the loop is bounded to prevent a redirect/refresh storm.

Why bound the loop? 451/452/450 all re-enter the loop. In a pathological race (e.g. the OM commits a flip exactly as the client refreshes, or the target itself reports a stale version) the client could ping-pong source↔target. A bounded attempt counter with small backoff, and re-resolving from the fresh map after a refresh, guarantees forward progress. Today the loop is unbounded.

ASK path — MIGRATED_ROUTE (451) in detail

This is the heart of "one RouteInfo is enough." While shard S is EXPORTING on the source, the client keeps routing S's keys to the source. For a key already exported, the source returns 451 with routeHint = target. The client retries only that key on the target, which is IMPORTING S and therefore accepts it.

Rules for the redirect client

  • One-shot. Use the redirect client for the immediate retry of this key only. Do not pin it for subsequent operations — the next call re-resolves through the map so that, once the shard commits, traffic naturally follows the new owner via 452.
  • Lazy, cached by address. getRedirectClient(address) reuses an existing pooled client when the target is already in clientMap (it usually is — both source and target exist in the pre-migration map), otherwise it creates and caches one. ShardingInfo.java:110-138.
  • Version to stamp on the ASK retry. The redirected request must carry a version the target will accept. Since the target legitimately owns/imports S at the same routeVersion the client is on, stamp the client's current cached version. If the target replies 452, fall through to a normal refresh; if 453, retry the same target. verify createRedirectClient stamps a version
  • Nested redirect. If the target itself returns 451 (rare; the key moved again), follow the new hint within the bounded attempt budget rather than looping unboundedly.
Pitfall to avoid. Never treat a 451 as a reason to mutate the cached map or bump routeVersion. Doing so would send all of shard S to the target while the source is still the owner of the not-yet-migrated keys — those keys would then bounce back, defeating the source anchor.

MOVED path — CLIENT_ROUTE_OUT_OF_DATE (452) and WRONG_ROUTE (450)

When the OM commits a shard to its new owner (Phase B) it bumps RouteInfo.version. The next time the client hits the old owner with the stale version, preExecute sees serverVersion > clientVersion and returns 452. The client then refreshes from the OM and re-resolves — now the key maps straight to the new owner.

Refresh discipline

  • Monotonic. refreshClientMap ignores a fetched map whose version is ≤ the cached version, so concurrent refreshes and an OM that briefly serves an older snapshot cannot regress the client. ShardingInfo.java:49-58.
  • Re-resolve, don't reuse. After a refresh the loop must call getShardingClient(key) again; the previously chosen cluster client may no longer own the key.
  • WRONG_ROUTE (450) is the safety net. 450 means the contacted cluster owns neither the live nor the importing copy of the key — the client's map is simply wrong (e.g. it skipped a version, or contacted a redirect address that has since handed the shard off). Treat it like 452: refresh from the OM and retry. Only after exhausting the bounded attempts should it surface as an error.
  • Coalesce refreshes. Many in-flight requests can hit 452 at once. The refresh should be single-flighted (one OM route() call, shared result) to avoid stampeding the OM; the version-monotone guard already makes redundant refreshes cheap no-ops.

Edge cases & correctness notes

Multi-key transactions and batches during migration

commitTransaction requires all keys to be in one shard via isInSameShard, and routes the batch by the first key. During migration two hazards appear:

  • Per-key redirect cannot apply to a batch. A 451 redirects a single key, but a transaction is one RPC over many keys. If a migrating shard's batch lands on the source while some of its keys already moved, the atomic Migrate command and the per-key lock on the server keep the batch serialized either fully before or fully after migration of those keys — the client simply retries the batch (on 451 follow the hint for the whole batch to the target; on 452 refresh and retry). The batch must not be split across source and target by the client.
  • Shard membership can change under a refresh. isInSameShard is evaluated against the cached map; after a flip the same keys may map to different clusters only if they were in different shards (they were not, by the in-one-shard check), so a same-shard batch stays same-cluster across the flip. Re-validate isInSameShard after any forced refresh before retrying. ShardingClientImpl.java:130-170; ShardingInfo.java:140-156.

Stale (follower) reads during migration

get(allowStale=true) is routed to a follower of the source. A follower may briefly lag the leader's migration progress, so a stale read of a just-migrated key can return an old value or trigger 451 from the follower. This is acceptable for stale reads by definition; clients needing exact post-migration values must use a leader read.

Redirect-client lifecycle

Addresses learned via 451 are cached in clientMap. Once a migration completes and the client refreshes, refreshClientMap rebuilds clientMap from the new map and reuses still-present clients while dropping ones no longer referenced. Transient redirect entries for clusters that remain in the new map survive; ones for clusters that left are garbage-collected on the next refresh. No explicit redirect eviction is required. ShardingInfo.java:59-74.

Version stamping on redirected requests

The single subtle invariant: a request must never reach a cluster carrying a version that cluster will reject as too new for no reason. Because source and target share the same routeVersion during Phase A, stamping the client's current cached version on both the normal and the ASK-redirected request is correct. After the flip, the only stale party is the client, which is corrected by 452.

OM unavailability

If route() fails during a forced refresh (452/450), the client cannot make progress for that key. It should retry the OM with backoff inside the bounded budget and surface a timeout/general error if the OM stays unreachable, rather than spinning. The existing single OM client is the refresh source. ShardingClientImpl.java:67-73.

Bottom line. One cached RouteInfo is sufficient for correct routing during online migration provided the client (a) anchors migrating-shard keys to the source, (b) honours MIGRATED_ROUTE as a per-key, map-preserving ASK redirect, and (c) refreshes only on CLIENT_ROUTE_OUT_OF_DATE/WRONG_ROUTE as a MOVED-style flip. The server's two-phase route and atomic Migrate command guarantee the per-key answers the client relies on. The remaining client work is hardening: fix 450, bound retries, make ASK one-shot, coalesce refreshes, and extend the same rules to batches.
