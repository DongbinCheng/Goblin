1背景与目标

Goblin 是构建在 Gringofts 之上的强一致 KV 存储系统。为突破单集群容量与吞吐上限，Goblin 通过分片（sharding）把 key 空间划分到多个 Object Store（OS）集群，实现水平扩展。

但当前实现为静态分片：分片总数固定为 212 = 4096，且在集群创建后无法在线增删集群、无法改变分片粒度（详见 第 2 节 与仓库 doc/sharding.md）。当单个 key 空间内部出现热点、或整体数据量增长超出预置集群容量时，系统缺乏弹性伸缩手段。

设计目标

目标说明
分片数动态化分片（shard）数量可在运行时增加/减少（分裂 Split / 合并 Merge），而不是编译期固定的 4096。
集群弹性伸缩可在线新增（scale-out）与下线（scale-in）OS 集群，并自动触发分片重平衡。
在线数据迁移迁移在后台增量进行，不断流：读写请求全程可服务。
强一致保障迁移过程中不丢失、不重复、不产生"读旧写新"错乱；沿用 Goblin 的强一致语义。
高可用任一步骤失败可回滚/重试；协调者与参与者宕机不破坏正确性。

非目标（Non-Goals）

  • 不改变 Goblin 单集群内部的 Raft 复制机制与 event-sourcing 模型。
  • 不在本方案实现跨分片分布式事务（现状即不支持跨集群事务，保持一致）。
  • 不引入外部协调服务（如独立 ZooKeeper/etcd）；复用 OM 作为元数据与协调中枢。

2现状分析（基于源码）

2.1 路由与分片模型

Goblin 采用三级映射：key → shard → cluster → column family。

图 2-1　当前静态分片的三级映射链路
  • key → shard：ObjectStore::keyToShardId() 计算 hash & ((1<<Shard::DEFAULT)-1)，Shard::DEFAULT = 12，即固定 4096 个分片。server/src/object-store/ObjectStore.h:130-134 protocols/common.proto:40-45
  • shard → cluster：由 OM 用一致性哈希 HashRing（RING_LENGTH = 4096）计算，写入 RouteInfo 下发给客户端与 OS。object-manager/route/HashRing.h:52
  • shard → column family：shardIdToColumnFamily() 用 shardId & ((1<<factor)-1)，kWorkingSetFactor = 4，即每个 OS 集群内部 16 个 working set（列族），每个列族承载 256 个 shard。ObjectStore.h:78-84,300

客户端侧完全对称：ShardingInfo.getShardingClient() 用 hash(key) % (1 << shardFactor) 选择集群客户端。client/.../internal/ShardingInfo.java

2.2 OM 与一致性哈希 HashRing

Object Manager（OM）本身也是一个 Raft 集群，保存全局集群集合 ClusterSetGlobalInfo（含 routeVersion、clusterIds、迁移任务 id 列表）。

  • HashRing::addClusterId() 把集群（可配虚拟节点 VIRTUAL_NODE_COUNT）投放到 [0,4096) 环上；每个 shard 顺时针归属到下一个集群节点。HashRing.cpp:66-102
  • extractShardConfig() 反推出 cluster → shard[] 映射，填入 RouteInfo.placementInfo。HashRing.cpp:107-135
  • 新增集群时，addClusterId(&clusterShardMap) 会计算出哪些 shard 需要从旧集群迁走——这正是重平衡的输入。

2.3 OS 与迁移框架（已有脚手架）

OS 侧已存在一套迁移原语，但尚未接通：

能力实现状态
扫描分片数据MigrationManager::ScanTask（按 working set 分批 scan）已实现
导出到目标集群ExportTask::exportLocalKeys() → MigrateBatch RPC客户端已实现
删除本地已迁数据ExportTask::deleteLocalKeys()已实现
迁移进度上报reportMigration() → OM OnMigration已实现
路由栅栏（迁移期读写重定向）preExecuteCallBack()：WRONG_ROUTE/MIGRATED_ROUTE/路由版本比对已实现
OM 侧重平衡与迁移任务创建onboardCluster() 中相关逻辑已注释禁用
MigrateBatch 服务端 CallDataRequestReceiver 未注册处理器缺失

preExecuteCallBack() 已经实现了迁移期的关键一致性逻辑：路由版本比 client 高 → 让 client 刷新（CLIENT_ROUTE_OUT_OF_DATE）；比 client 低 → 服务端异步刷新并让 client 重试（SERVER_ROUTE_OUT_OF_DATE）；导出中的 key 若本地已删则回 MIGRATED_ROUTE + 目标集群地址。ObjectStore.cpp:109-191

2.4 现状痛点

Gap
  1. 分片数硬编码：Shard::DEFAULT=12 与 RING_LENGTH=4096 编译期固定，无法改变分片粒度，热点分片无法进一步细分。
  2. 重平衡链路断开：onboardCluster() 里生成迁移任务的代码被注释，新集群加入后不会真正迁移数据。
  3. 服务端 MigrateBatch 缺失：导出方能发，但接收方没有 CallData，迁移无法闭环。
  4. 并发迁移受限：fillRouteAndMigrationInfo() 假设"同一时刻只有一个迁移任务"。

3开源方案借鉴

动态分片是分布式存储的通用课题，主流方案可归纳为两大流派，本方案取两者之长并结合 Goblin 特性裁剪。

系统分片模型动态伸缩方式 & 可借鉴点
Redis Cluster固定 16384 个 hash slot槽数固定、槽→节点映射可变；MIGRATING/IMPORTING 状态 + ASK/MOVED 重定向。可借鉴：稳定的大粒度逻辑槽 + 客户端重定向（与 Goblin MIGRATED_ROUTE 高度相似）。
Vitesskeyspace 按 keyrange 分片Resharding：先建目标 shard，VReplication 增量复制，SwitchTraffic 原子切流。可借鉴：先复制后切流、双写追平、可回退。
TiKV / PDRegion（连续 key range），可 Split/MergePD 调度、Region 自动分裂合并、按负载迁移 leader/peer。可借鉴：真正的分裂/合并 + 中心调度器。
HBaseRegion 自动 split阈值触发 split，父 region 短暂只读。可借鉴：容量/热点触发的自动分裂。
KafkaTopic partition只增不减、reassignment 迁移副本。教训：分区不可缩会带来长期负债 → Goblin 需支持 merge。
DynamoDB一致性哈希 + 自适应分裂后台按热点自动分裂 partition，对用户透明。可借鉴：热点驱动 + 全程在线。
结论 Goblin 现状最接近 Redis Cluster（大粒度逻辑槽 + 客户端重定向）；已具备 routeVersion、MIGRATED_ROUTE、per-shard 迁移原语。因此本方案以 "可分裂的逻辑槽" 为骨架，融合 Vitess 的"先复制后切流" 与 TiKV 的"中心调度 + Split/Merge"，最大程度复用已有代码。

4设计总览

4.1 核心思想

把"分片数动态变化"拆解为两个正交维度，分别独立演进、组合使用：

维度 A · 放置伸缩（Placement）

改变 shard → cluster 映射：新增/下线集群时，把部分 shard 从源集群搬到目标集群。分片总数不变，仅改变归属。复用现有 HashRing + 迁移原语即可打通。

维度 B · 粒度伸缩（Granularity）

改变 key → shard 的分片总数：对某分片做 Split（一分为二） 或对相邻分片做 Merge（合二为一）。这是真正意义上的"shard 个数动态变化"。

两者共享同一套在线迁移协议（第 6 节）与路由版本栅栏，从而以统一机制保证不断流。

4.2 分层分片模型

引入"逻辑槽（logical slot）+ 动态分片位（dynamic shard bits）"模型，替代固定的 212：

图 4-1　逻辑槽（稳定路由锚点）+ 每槽可变分裂深度（动态粒度）
为什么这样分层 逻辑槽 M 保持恒定 → 客户端路由算法与 RouteInfo 结构基本不变；粒度变化被封装在"槽内分裂深度"里，只影响服务端列族与迁移单元。这样"分片数动态变化"不会破坏客户端与已有 4096→16384 路由假设，改造面最小、风险最低。

4.3 组件职责

组件新增/变更职责
OM · ShardCatalog 新增全局分片目录：记录每个 slot 的 splitDepth、每个 shard 的状态（Normal/Splitting/Merging/Migrating）与归属集群；作为迁移的唯一真相源。
OM · Rebalancer 新增调度器：根据触发信号（扩缩容/热点/容量）产出迁移计划（一组 MigrationTask），驱动状态机推进，支持并发多任务。
OM · ClusterSetManager 打通接通 onboardCluster() 中被注释的重平衡逻辑；实现 removeCluster()；驱动 Split/Merge。
OS · MigrationManager 增强支持"分片子集"迁移与"槽内 range"迁移；补齐 MigrateBatch 服务端 CallData；支持并发多任务与断点续传。
OS · preExecuteCallBack 扩展在既有路由栅栏基础上，增加 Split/Merge 期间的双活读写判定。
Client · ShardingInfo 小改把 shardFactor 常量替换为 RouteInfo 下发的每槽分裂深度；重定向逻辑已具备。

5动态分片模型详解

5.1 逻辑槽 vs 物理分片

定义（M 为常量槽位数，如 14；d(s) 为槽 s 的分裂深度）：

SlotId  = hash(key) >> (64 - M)                 // 稳定：客户端一致性路由锚点
subBits = (hash(key) >> (64 - M - d)) & ((1<<d)-1)  // 槽内子分片选择位
ShardId = encode(SlotId, d, subBits)            // 全局唯一物理分片号
                                                 // d=0 → 整槽一个分片（默认）
  • 默认 d=0：等价于当前"一个槽=一个分片"，与现状 4096/16384 分片行为一致，平滑兼容。
  • 分裂：d → d+1，一个分片按 subBits 最高位裂成两个子分片，可独立放置到不同集群。
  • 合并：相邻兄弟子分片 d → d-1 合回父分片。
  • ShardId 采用可解析编码（如 SlotId 高位 | depth | subBits），使 shardIdToColumnFamily() 与 HashRing 都能从中恢复分裂层级。
兼容性 当所有槽 d=0 时，本模型的 ShardId 空间与列族映射可退化为现有 hash & (2^M-1)，因此升级过程可"零迁移"从静态分片切换到动态分片模型。

5.2 Shard 分裂（Split）

触发条件（任一，由 Rebalancer 评估）：分片数据量/键数超阈值、写入 QPS 热点、目标集群需要更细粒度以承接迁移。

图 5-1　Shard 分裂状态机（不断流）
  1. Prepare：OM 在 ShardCatalog 中将 d→d+1，登记子分片 S0/S1（初始与 S 同集群，或指定目标集群），状态置 SPLITTING，但暂不提升 routeVersion（客户端仍按父分片 S 路由）。
  2. Copy：若子分片需迁到别的集群，走在线迁移协议（第 6 节）复制存量数据。若原地分裂（同集群、仅拆列族），则只需重打列族标签，无跨网络拷贝。
  3. Dual-Write 追平：Copy 期间对 S 的新写入，按新的 subBits 同步落到 S0/S1，保证增量不丢（详见 6.2）。
  4. Switch：追平后，OM 在一个 Raft 事务里原子地把 S0/S1 置 NORMAL、更新 placement、routeVersion++。客户端下次请求即感知新路由。
  5. Cleanup：源分片 S 的冗余副本/旧列族被回收。

5.3 Shard 合并（Merge）

触发条件：相邻兄弟分片长期低负载、集群缩容需要归并碎片。合并是分裂的逆过程，同样不断流：

  1. Prepare：选定同一父槽下的兄弟对 S0/S1（d 相同、前缀相邻），登记父分片 S(d-1)，状态 MERGING。
  2. Colocate & Copy：若二者不在同一集群，先把其中一个迁到另一个所在集群（复用迁移协议），使数据物理同址。
  3. Dual-Write 追平：合并期对 S0/S1 的写入同时写入父分片视图。
  4. Switch：原子将 S0/S1 → S(d-1)，d--，routeVersion++。
约束 只允许合并"同父、同深度、前缀相邻"的兄弟分片（buddy-merge），保证 ShardId 编码可逆、避免 range 空洞。这是从 Redis/TiKV 合并约束中提炼的安全规则。

6在线迁移协议（不断流核心）

6.1 迁移阶段

无论是 Placement 迁移、Split 还是 Merge，底层统一为一个四阶段迁移协议（复用并强化现有 MigrationManager）：

阶段动作可用性
P1 Snapshot 复制源集群 ScanTask 分批扫描迁移分片存量数据，经 MigrateBatch 写入目标集群（幂等 upsert，带 version）。读写正常，全部由源集群服务。
P2 增量追平源集群对迁移中分片开启变更转发/双写，把 P1 期间及之后的新写入同步到目标；直至 lag→0。读写正常；写入额外转发一份。
P3 原子切流OM 事务：迁移分片归属改为目标集群，routeVersion++，源标 EXPORTING→交出，目标标 IMPORTING→IN_SERVICE。切换瞬间旧路由请求被 MIGRATED_ROUTE/*_ROUTE_OUT_OF_DATE 重定向重试，无失败。
P4 清理源集群删除已迁数据（deleteLocalKeys），关闭双写；OM 移除迁移任务。读写正常，全部由目标集群服务。

6.2 不断流一致性机制

关键在于 P2/P3 交界处如何保证"不丢、不重、不错序"。设计如下：

读路径
  • 切流前：由源集群服务（迁移分片仍归源）。
  • 切流后：客户端持旧 routeVersion 命中源集群 → 源在 preExecuteCallBack 判定该 key 已迁走（本地 meta not found）→ 返回 MIGRATED_ROUTE + 目标地址，客户端立即重定向到目标（现状已实现）。ObjectStore.cpp:172-184
写路径（双写 + 版本仲裁）
  • P2 期间，源集群对迁移分片的每次写，除本地 commit 外，异步转发 MigrateBatch 到目标；MigrateBatch 以 (key, version) 幂等 落库——目标已有更高 version 则忽略，保证 P1 快照与 P2 增量、以及乱序到达时以最新 version 收敛。
  • P3 切流用 OM 单条 Raft 事务完成，保证"源停止接受该分片写"与"目标开始接受"之间无重叠窗口；切流后源对该分片写入直接回重定向，不再本地落库。
迁移中的写去哪 为避免"源已删、目标未收"的空窗，采用 先复制后删除：ExportTask 先 exportLocalKeys() 确认目标 ACK 成功，再 deleteLocalKeys()（现状顺序已如此）。删除失败的 key 会重新入 ScanTask 重试，天然幂等。MigrationManager.cpp:92-162

6.3 路由版本栅栏（Fencing）

每次请求携带 RequestHeader.routeVersion，服务端在 preExecuteCallBack 三向比对：

比较含义动作
server > client客户端路由过期回 CLIENT_ROUTE_OUT_OF_DATE，客户端向 OM 拉新路由后重试。
server < client服务端路由过期服务端异步 refreshRouteInfo()，回 SERVER_ROUTE_OUT_OF_DATE 让客户端重试。
相等但 key 不属本集群切流后残留请求回 WRONG_ROUTE 或 MIGRATED_ROUTE+目标地址。

该栅栏保证：无论客户端/服务端谁的视图旧，最终都收敛到最新路由且请求最终成功，是不断流的兜底。此机制现状已实现，动态分片直接复用。ObjectStore.cpp:120-135

9容错与幂等

故障场景处理
源 OS 迁移中宕机迁移任务持久化于 OM；新 leader 从 ShardCatalog 状态恢复，未完成的 shard 重新 ScanTask。MigrateBatch 幂等，重复导出安全。
目标 OS 宕机Raft 保证目标集群自愈；exportLocalKeys 重试直至 ACK 成功后才删源，无数据丢失。MigrationManager.cpp:107-126
OM leader 切换OM 为 Raft 集群；迁移编排状态在日志中，新 leader 续跑，得益于 event-sourcing 的状态可复现。
Switch 事务失败routeVersion 不提升 → 视图保持切流前状态 → 迁移可安全重试或整体回滚到 NORMAL。
客户端持极旧路由路由版本栅栏保证多跳重定向后最终命中，最坏情况多几次重试，不返回错误结果。
删除失败残留deleteLocalKeys 失败的 key 重新入队 ScanTask 重删，幂等收敛。MigrationManager.cpp:151-158
正确性不变式 ① 任一时刻每个 key 恰有一个"权威分片"提供强一致读写；② 切流是原子 Raft 事务，无双主写窗口；③ 先复制确认、后删除源，保证不丢；④ 版本幂等保证不重、乱序收敛。

10可用性与限流

  • 后台低优先级迁移：MigrationManager 使用独立线程池（现 kMigrationThreadNum=10），迁移与前台请求隔离；引入可配置的批大小/速率限流（如每秒 MigrateBatch 条数），避免抢占前台 IO。MigrationManager.h:135
  • 小步分批：ScanTask 已按 kScanMaxBatch=100 分批扫描，天然增量、可暂停/续传。
  • 并发控制：Rebalancer 限制全局并发迁移任务数，优先保证在迁移集群的前台 SLA。
  • 热点感知调度：借鉴 DynamoDB/TiKV，Rebalancer 依据分片 QPS 与容量指标选择分裂点与迁移目标，避免"迁完仍热"。
  • 灰度切流：Switch 以分片为最小单位逐个提交，单次切流影响面小；失败只影响该分片且可回滚。
  • 可观测性：复用 reportMigration 进度上报 + Prometheus 指标（迁移 lag、剩余分片、重定向率）供运维决策。

11分阶段实施计划

阶段目标主要工作
M1打通 Placement 迁移（分片数不变）补 MigrateBatchCallData；取消注释 onboardCluster 迁移逻辑；打通 Start/End/Report 全链路；端到端验证新增集群后数据真正迁移、不断流。
M2缩容支持实现 removeCluster()；下线集群前把其分片迁往其余集群；HashRing 删除节点重平衡。
M3引入分层分片模型落地 SlotId + splitDepth 编码；ShardCatalog；keyToShardId/shardIdToColumnFamily/客户端 ShardingInfo 改为读 RouteInfo 动态参数；默认 d=0 零迁移兼容。
M4Shard 分裂SplitShard RPC + 状态机 + 双写追平 + 原子切流；容量/热点触发器。
M5Shard 合并Buddy-merge RPC + 状态机；低负载/缩容触发。
M6调度器与限流Rebalancer 自动决策；并发多任务；速率限流；可观测性与灰度开关。

M1–M2 复用现有脚手架、改造面小、收益最大，建议优先落地；M3 起进入真正的"分片数动态变化"。

12风险与权衡

议题权衡与选择
逻辑槽 M 的取值M 太小限制最大集群数；太大增加元数据。建议 M=14（16384 槽），对齐 Redis 经验且留足扩展空间。分裂深度按需局部增长，不必全局提高 M。
原地分裂 vs 跨集群分裂原地分裂仅重打列族标签，几乎零成本，适合先分裂再择机迁移；跨集群分裂 = 分裂 + 迁移，成本高但一步到位。方案两者皆支持，由 Rebalancer 择优。
双写开销P2 双写增加写放大与延迟。通过限流、仅对迁移中分片开启、lag 收敛后尽快切流来控制窗口。
跨分片事务分裂/合并可能改变 key 的分片归属，影响 RMSTRX 迷你事务定位（现固定 RMSTRX_SHARD_IDX）。需保证事务键的分片在迁移期间的一致定位，必要时对事务键所在槽禁用分裂。ObjectStore.h:47-48
客户端兼容老客户端用固定 shardFactor。通过 routeVersion 栅栏可容忍其暂时落后；建议客户端升级为读取 RouteInfo 动态槽参数。
