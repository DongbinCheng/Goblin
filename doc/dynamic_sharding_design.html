Goblin Dynamic Sharding

Design proposal & a guided walkthrough of the migration code already present in the repository.

TL;DR

Goblin splits the key space into 4096 fixed shards (hash(key) & (2^12-1)). The Object Manager (OM) is a Raft cluster that owns a consistent-hash ring mapping shard → cluster and publishes it as a versioned RouteInfo. Each Object Store (OS) is itself a Raft cluster that stores the data for the shards it owns.

The scaffolding for dynamic sharding already exists — an OM-side migration orchestrator (ClusterProxy/ClusterClient/Migration), an OS-side MigrationManager (scan → export → delete), StartMigration/EndMigration RPCs, migration-aware routing codes (WRONG_ROUTE, MIGRATED_ROUTE, CLIENT/SERVER_ROUTE_OUT_OF_DATE), and a Raft-persisted migration task state machine. But the pieces are not wired together end-to-end: the trigger that creates migration tasks is commented out, the import RPC is never registered, and failure / remove-cluster paths are stubs.

2. How static sharding routes a request today IMPLEMENTED

Every OS request runs through a pre-execute routing gate (ObjectStore.cpp:109-191) before the command reaches the KV engine. This gate is already migration-aware — it knows how to reject, redirect, or wait.

Key insight: the route is a version handshake. Client and server each carry a routeVersion; mismatch is resolved by the client refreshing from OM and retrying. This same versioning is what makes a live route change (i.e. dynamic sharding) safe.

How the ring decides what moves IMPLEMENTED

When cluster C_new is hashed onto the ring, it lands between two existing points. Only the arc immediately clockwise of its position changes ownership — this is classic consistent hashing, so adding one cluster moves roughly 1/N of the shards, not the whole space.

4. Export & import: moving the data MECHANISM PRESENT

A shard is not a physical partition; it is logically grouped into a RocksDB column family (“working set”) via wsId = shardId & ((1<<factor)-1) (ObjectStore.h:78-84). Migration scans the working set, filters by the shard ids being moved, ships them to the target, then deletes locally.

Important gap: on the target, migrateBatchAsync exists but there is no MigrateBatchCallData registered in RequestReceiver.cpp:76-84 (only Connect/Get/Put/Delete/Trans/Generate/StartMigration/EndMigration/Watch are spawned). So a MigrateBatch RPC has no server handler today — the import side is effectively dead until this is wired up.

5. Migration state machine

The task lives in two coupled state machines: the migration task status (persisted in OM Raft) and each cluster's status (IN_SERVICE ↔ EXPORTING/IMPORTING).

7. Why availability is preserved during a move

Dynamic sharding is only useful if the cluster keeps serving while data moves. Goblin's design relies on four already-present mechanisms working together:

WindowMechanismClient experienceCode
Before route flipSource still owns the shard; serves normally while exporting. Normal reads/writes.ObjectStore.cpp:159-191
Key already exported & deleted on sourceSource returns MIGRATED_ROUTE with routeHint to target.Transparent redirect & retry.ObjectStore.cpp:178-183
Route changed but client staleVersion handshake: WRONG_ROUTE / CLIENT_ROUTE_OUT_OF_DATE → client refreshes from OM.One refresh + retry.ObjectStore.cpp:120-171
Target receiving shardTarget in IMPORTING accepts keys for shards it is about to own.Writes land on target.ObjectStore.cpp:161-166
Because each moved key carries its original version, the strong-consistency / CAS guarantees survive the move: a client that read version v on the source can still CAS against v on the target. (KVImportCommand preserves version & ttl.)
Consistency caveat to design carefully: the export “copy then delete” is not atomic across two Raft groups. A write that arrives on the source after its key was exported but before the route flips must not be silently lost. The redirect path (MIGRATED_ROUTE on readMeta not-found) is the intended guard, but it currently only triggers on read-meta miss — a per-shard “sealed” / freeze marker would make this airtight.

Suggested incremental delivery order

  1. Wire the import side (gap 2): add MigrateBatchCallData, register it in RequestReceiver, route to migrateBatchAsync. Without this nothing can be imported.
  2. Re-enable the trigger (gaps 1,3): uncomment / rebuild onboardCluster's rebalance loop so adding a cluster produces a NOT_START migration task and sets EXPORTING/IMPORTING.
  3. Close the consistency window (gap 8): introduce a per-shard sealed marker on the source so post-export writes to a moved shard return MIGRATED_ROUTE deterministically (not only on read-meta miss).
  4. Robust progress + failure (gaps 4,6,7): persist RUNNING/FAILED, bound the retry, add resume-from-progress, replace asserts with recoverable errors.
  5. Scale-in (gap 5): implement RemoveCluster as the reverse migration (drain shards to remaining clusters using HashRing::deleteClusterId).
  6. Leadership primitive (gap 9): replace dummy-get checks with a dedicated lightweight command.
Bottom line: Goblin already contains a coherent dynamic-sharding skeleton — consistent-hash rebalancing, a Raft-persisted migration task, leader-aware orchestration RPCs, a scan/export/delete pipeline, and migration-aware routing codes. The remaining work is mostly connecting these pieces (import handler + re-enabling the trigger) and hardening the edges (atomic shard seal, failure recovery, scale-in) rather than designing from scratch.
