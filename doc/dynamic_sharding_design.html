Goblin 集群弹性伸缩（Dynamic Clustering）详细设计方案

分片总数固定为 4096；通过改变集群数量（M → N）把 4096 个分片在集群间重新划分，每个分片始终只属于一个集群。

重点阐述：① 重新划分后如何迁移某个分片的数据；② 如何处理正在被迁移分片的读写请求。迁移全程不断流。

基于 DongbinCheng/Goblin 现有源码（构建于 Gringofts Raft 框架之上）设计。

1背景与目标

Goblin 是构建在 Gringofts 之上的强一致 KV 存储系统。为突破单集群容量与吞吐上限，Goblin 把 key 空间静态划分为 212 = 4096 个分片（shard），再由 Object Manager（OM）用一致性哈希把这 4096 个分片映射到若干 Object Store（OS）集群。

本方案不改变分片总数：4096 个分片的划分粒度保持固定。真正需要弹性的是集群的数量——当整体数据量或吞吐增长时需要新增集群（scale-out），当负载回落时需要下线集群（scale-in）。因此核心问题收敛为一句话：

问题定义 如何把这 4096 个分片的数据，从当前的 M 个集群重新划分（re-partition）到 N 个集群？无论怎样划分，每个分片的全部数据始终只属于一个集群（分片是迁移与归属的最小单位，不会被拆开）。

围绕这个问题，本文档需要详尽回答两件事（也是相较旧版设计需要补强的重点）：

  1. 重新划分后，某个分片的数据如何迁移——从源集群搬到目标集群的完整协议（第 6 节）。
  2. 正在被迁移的分片，其读写请求如何处理——迁移窗口内不丢、不重、不断流的读写路由（第 7 节）。

设计目标

目标说明
集群数动态化集群数量可在运行时从 M 变为 N（扩容 scale-out / 缩容 scale-in），无需停机重建。
分片重划分集群数变化后，OM 自动重算 shard → cluster 映射，仅迁移归属发生变化的分片，迁移量最小化。
分片不可拆分片总数恒为 4096；每个分片作为整体迁移，任一时刻只归属一个集群。
在线数据迁移迁移在后台增量进行，不断流：迁移中分片的读写请求全程可服务。
强一致保障迁移过程中不丢失、不重复、不产生"读旧写新"错乱；沿用 Goblin 的强一致语义。
高可用任一步骤失败可回滚/重试；协调者（OM）与参与者（OS）宕机不破坏正确性。

非目标（Non-Goals）

  • 不改变分片总数（4096）、不做 shard 分裂/合并（Split/Merge）——分片粒度固定，本方案只调整分片到集群的归属。
  • 不改变 Goblin 单集群内部的 Raft 复制机制与 event-sourcing 模型。
  • 不在本方案实现跨分片/跨集群分布式事务（现状即不支持，保持一致）。
  • 不引入外部协调服务（如独立 ZooKeeper/etcd）；复用 OM 作为元数据与协调中枢。

2现状分析（基于源码）

2.1 路由与分片模型

Goblin 采用三级映射：key → shard → cluster → column family。

图 2-1　当前静态分片的三级映射链路
  • key → shard：ObjectStore::keyToShardId() 计算 hash & ((1<<Shard::DEFAULT)-1)，Shard::DEFAULT = 12，即固定 4096 个分片。server/src/object-store/ObjectStore.h:130-134 protocols/common.proto:40-45
  • shard → cluster：由 OM 用一致性哈希 HashRing（RING_LENGTH = 4096）计算，写入 RouteInfo 下发给客户端与 OS。object-manager/route/HashRing.h:52
  • shard → column family：shardIdToColumnFamily() 用 shardId & ((1<<factor)-1)，kWorkingSetFactor = 4，即每个 OS 集群内部 16 个 working set（列族），每个列族承载 256 个 shard。ObjectStore.h:78-84,300

客户端侧完全对称：ShardingInfo.getShardingClient() 用 hash(key) % (1 << shardFactor) 选择集群客户端。client/.../internal/ShardingInfo.java

2.2 OM 与一致性哈希 HashRing

Object Manager（OM）本身也是一个 Raft 集群，保存全局集群集合 ClusterSetGlobalInfo（含 routeVersion、clusterIds、迁移任务 id 列表）。

  • HashRing::addClusterId() 把集群（可配虚拟节点 VIRTUAL_NODE_COUNT）投放到 [0,4096) 环上；每个 shard 顺时针归属到下一个集群节点。HashRing.cpp:66-102
  • extractShardConfig() 反推出 cluster → shard[] 映射，填入 RouteInfo.placementInfo。HashRing.cpp:107-135
  • 新增集群时，addClusterId(&clusterShardMap) 会计算出哪些 shard 需要从旧集群迁走——这正是重平衡的输入。

2.4 现状痛点

Gap
  1. 重平衡链路断开：onboardCluster() 里"新增集群后生成迁移任务"的代码被整段注释（注释写着 "Skip migration as only static sharding is supported currently"），新集群加入后 HashRing 虽已算出待迁分片，但不会真正迁移数据。ClusterSetManager.cpp:412-433
  2. 缩容未实现：removeCluster() 为空，无法在线下线集群并把其分片迁走。
  3. 服务端 MigrateBatch 缺失：导出方 ExportTask 能通过 migrateBatch() 发送批数据，但 RequestReceiver 未注册 MigrateBatchCallData，接收方无处落地，迁移无法闭环。RequestReceiver.cpp:76-84
  4. 并发迁移受限：fillRouteAndMigrationInfo() 明确假设"同一时刻只有一个迁移任务"（currently, there are only one migration in process）；一次扩缩容通常涉及多个源集群，需要支持多任务并发。
好消息 迁移所需的核心一致性原语已经存在且可复用：per-shard 扫描/导出/删除（MigrationManager）、迁移进度上报（reportMigration）、以及最关键的迁移期读写路由判定（preExecuteCallBack 已实现 IMPORTING/EXPORTING 双向处理与 MIGRATED_ROUTE 重定向）。本方案的工作主要是打通编排链路，而非从零构建一致性机制。

3开源方案借鉴

动态分片是分布式存储的通用课题，主流方案可归纳为两大流派，本方案取两者之长并结合 Goblin 特性裁剪。

系统分片模型动态伸缩方式 & 可借鉴点
Redis Cluster固定 16384 个 hash slot槽数固定、槽→节点映射可变；MIGRATING/IMPORTING 状态 + ASK/MOVED 重定向。可借鉴：稳定的大粒度逻辑槽 + 客户端重定向（与 Goblin MIGRATED_ROUTE 高度相似）。
Vitesskeyspace 按 keyrange 分片Resharding：先建目标 shard，VReplication 增量复制，SwitchTraffic 原子切流。可借鉴：先复制后切流、双写追平、可回退。
TiKV / PDRegion（连续 key range），可 Split/MergePD 调度、Region 自动分裂合并、按负载迁移 leader/peer。可借鉴：真正的分裂/合并 + 中心调度器。
HBaseRegion 自动 split阈值触发 split，父 region 短暂只读。可借鉴：容量/热点触发的自动分裂。
KafkaTopic partition只增不减、reassignment 迁移副本。教训：分区不可缩会带来长期负债 → Goblin 需支持 merge。
DynamoDB一致性哈希 + 自适应分裂后台按热点自动分裂 partition，对用户透明。可借鉴：热点驱动 + 全程在线。
结论 本方案与 Redis Cluster 的模型最为契合：逻辑分片数固定（Redis 16384 槽 / Goblin 4096 分片），只改变"分片 → 节点/集群"的映射，并用客户端重定向（Redis MOVED/ASK ≈ Goblin MIGRATED_ROUTE）承接迁移期请求。同时借鉴 Vitess "先复制后切流、增量追平、可回退" 保证迁移不断流。不采用 TiKV/HBase 的 Split/Merge——因为本需求明确固定分片粒度，只调整集群数量。Goblin 已具备 routeVersion 栅栏、MIGRATED_ROUTE 重定向与 per-shard 迁移原语，落地成本低。

4设计总览

4.1 核心思想

整个方案只围绕一个可变量展开：shard → cluster 的映射。key→shard（4096 固定）与 shard→column family 都保持不变。集群数从 M 变到 N，本质上是三步：

图 4-1　集群数 M→N 的三步：重算映射 → 计算差异 → 逐分片迁移
  • 分片是迁移的最小单位：一个分片的所有 key 要么全在源集群，要么全在目标集群，切流是分片级原子事件——这天然满足"每个分片只属于一个集群"的不变式。
  • 一致性哈希最小化迁移：M→N 时，绝大多数分片归属不变；一致性哈希（含虚拟节点）保证只有约 Δ = |迁移分片| ≈ 4096 × (1 − M/N)（扩容）个分片需要搬迁，避免全量重排。
  • 复用统一迁移协议：无论扩容还是缩容，每个"归属改变的分片"都走同一套四阶段在线迁移协议（第 6 节）与同一套路由栅栏（第 7 节）。

4.2 组件职责

组件新增/变更职责

OM · HashRing 复用addClusterId(&map) 已能算出"新集群将从哪些旧集群接管哪些分片"；deleteClusterId() 支持缩容重排。作为 shard→cluster 的唯一计算源。HashRing.cpp:55-135

5分片重新划分（Re-partition）

5.1 划分不变式

无论 M→N 如何变化，系统始终维持以下不变式：

Invariants
  1. I1 · 全覆盖：4096 个分片的并集恰好覆盖整个 key 空间，无空洞、无重叠。
  2. I2 · 单一归属：任一时刻，每个分片恰好归属一个集群（迁移中的分片有唯一"权威集群"，见 6.3/7）。
  3. I3 · 整体迁移：分片是迁移的最小单位，其 key 集合不被拆分到两个集群。
  4. I4 · 版本单调：每次归属变更都伴随 routeVersion 单调递增，作为新旧视图的分界。

5.2 扩容：M → N（N > M）

新增集群时，OM 复用一致性哈希 HashRing 计算需要接管的分片，只迁移这部分，其余分片原地不动。

图 5-1　扩容：HashRing 直接算出"哪些源集群的哪些分片需迁往新集群"
  1. 登记集群：onboardCluster() 把新集群置 IN_SERVICE，并对已在环上的集群与新集群调用 addClusterId()。
  2. 算差异：addClusterId(newId, &clusterShardMap) 返回 map<源集群, 待迁分片[]>——正是"从哪迁、迁哪些"。HashRing.cpp:66-102
  3. 生成迁移任务：对 map 中每个源集群创建一个 MigrationTask（源→新集群 + 分片列表），源集群置 EXPORTING，新集群置 IMPORTING；整批在一个 OM Raft 事务中持久化（打通 onboardCluster() 中现被注释的这段逻辑）。ClusterSetManager.cpp:412-433
  4. 并发迁移：多个源集群的任务并行推进（需解除"单任务"假设，见第 9 节）。

5.3 缩容：M → N（N < M）

缩容是扩容的镜像：把待下线集群持有的分片全部迁往保留集群，然后从环上摘除该集群。

  1. 标记下线：removeCluster()（当前为空，需实现）把目标集群置 EXPORTING，停止其接收新分片。
  2. 重算落点：HashRing::deleteClusterId(id) 从环上删除该集群的所有虚拟节点；再用 extractShardConfig() 反推新的 cluster→shard[]，得出该集群原持分片的新归属（一致性哈希保证只在相邻集群间重排）。HashRing.cpp:55-64,107-135
  3. 生成迁移任务：待下线集群作为源，其分片按新落点分组，为每个目标集群建一个迁移任务；目标集群置 IMPORTING。
  4. 确认后摘除：所有分片迁移完成（routeVersion++ 生效、无残留请求）后，才真正将该集群置 OUT_OF_SERVICE 并从集群集合移除。
安全序 缩容必须先迁空、再摘除：只有当下线集群不再是任何分片的权威集群、且客户端路由都已刷新到不指向它之后，才能停机。中途任一步失败都可回滚（保持其 EXPORTING 或退回 IN_SERVICE）。

一次扩缩容 = 一个迁移计划（Plan）= 一组按源集群拆分的 MigrationTask。每个任务覆盖若干分片，其生命周期由 OM 以 Raft 事务持久化，因而 100% 可复现、可断点续跑（复用 Goblin event-sourcing）。

6分片数据迁移（如何搬一个分片）

本节回答需求的第一问：重新划分后，某个分片的数据如何从源集群迁到目标集群。底层是一个四阶段协议，复用并强化现有 MigrationManager。

6.2 增量追平与"先复制后删除"窗口

不丢（先复制后删除）
  • exportLocalKeys() 内部对 MigrateBatch 重试直到目标全部 ACK 成功才返回；随后 deleteLocalKeys() 才删源。目标未确认收到前，源数据绝不删除，杜绝"源已删、目标未收"空窗。MigrationManager.cpp:100-124
  • 删除失败的 key 会被重新封装成新的 ScanTask 重新导出/删除，天然幂等收敛。MigrationManager.cpp:143-162
不重、乱序收敛（版本幂等）
  • 每条 MigrateBatch 条目携带 version；目标落库时若已有更高 version 则忽略。于是 P1 快照与 P2 增量、以及网络乱序到达的多条写，都会收敛到最新版本。MigrationManager.cpp:88-108
  • 需补齐的服务端 MigrateBatchCallData 必须落实这套幂等 upsert 语义（当前接收器缺失，是闭环关键）。RequestReceiver.cpp:76-84

6.3 原子切流（唯一权威的移交）

切流（P3）是把某分片的"权威集群"从源改为目标的原子时刻，用 OM 一条 Raft 事务完成，保证不存在"源与目标同时接受该分片写"的双主窗口：

  • 事务提交前：分片仍属源集群，源为权威（此时目标处于 IMPORTING，仅接收迁移写，不对外服务该分片）。
  • 事务提交后：routeVersion++，分片归属=目标；源集群对该分片的后续请求一律转为重定向（见第 7 节），不再本地落库。

由于切流以分片为最小单位提交，一次可只切一个或一小批分片，失败仅影响该分片且可回滚（routeVersion 不提升即视图不变）。这满足不变式 I2/I4。

7迁移期读写请求处理（正在被迁移的分片）

本节回答需求的第二问：当一个分片正在迁移时，落到它上面的读写请求如何处理。核心机制现状已实现于 ObjectStore::preExecuteCallBack()：先做路由版本栅栏，再按本集群角色（EXPORTING 源 / IMPORTING 目标）逐 key 判定放行或重定向。ObjectStore.cpp:109-191

7.1 路由版本栅栏（Fencing）

每个请求携带 RequestHeader.routeVersion；服务端与本地 routeVersion 三向比对，先解决"谁的路由视图旧"：

比较含义动作
server > client客户端路由过期回 CLIENT_ROUTE_OUT_OF_DATE，客户端向 OM 拉新 RouteInfo 后重试。ObjectStore.cpp:120-123
server < client服务端路由过期服务端异步 refreshRouteInfo()，回 SERVER_ROUTE_OUT_OF_DATE 让客户端稍后重试。ObjectStore.cpp:125-131
相等视图一致进入下面的 per-shard 归属判定（7.2 / 7.3）。

该栅栏保证：无论客户端或服务端谁的视图旧，最终都收敛到最新路由，请求最终成功——这是不断流的兜底。

7.2 源集群侧（EXPORTING）：切流前服务、切流后重定向

迁移中分片的源集群状态为 EXPORTING。对落到迁移分片的 key，源集群按"该 key 是否已被迁走"分流：

源集群逻辑（已实现）
  • 若 key 的分片仍属本集群（未切流）→ 正常本地读写，由源服务。
  • 若本集群状态 EXPORTING 且该分片在迁移集合中 → 读该 key 的 meta：
    • readMeta 命中（本地仍有）→ 尚未迁走，本地服务。
    • readMeta 返回 NotFound（已迁并删除）→ 回 MIGRATED_ROUTE + 目标集群地址（getTargetCluster()），客户端据此重定向到目标集群重试。ObjectStore.cpp:172-186

因此在源集群侧，一个迁移分片的读写始终有确定去向：数据还在就地服务，数据已迁就重定向，绝不出现"两边都不认"或"两边都认"。

7.3 目标集群侧（IMPORTING）：接管中的分片放行

目标集群状态为 IMPORTING。它尚未在最新 RouteInfo 中正式拥有该分片（切流前），但为了承接 P1/P2 的迁移写、以及切流后被重定向来的请求，需要对"正在接管的分片"放行：

目标集群逻辑（已实现）
  • 若 key 的分片按 RouteInfo 尚不属本集群，但本集群 IMPORTING 且该分片在迁移集合中 → 放行（continue），允许本地处理（承接迁移写入与被重定向的请求）。ObjectStore.cpp:161-169
  • 若分片既不属本集群、又不在接管集合 → 回 WRONG_ROUTE，让客户端纠正路由。

7.4 读写决策全表

本集群角色分片归属（RouteInfo）在迁移集合?key 是否已迁走动作
任意———routeVersion 不一致 → *_ROUTE_OUT_OF_DATE，刷新后重试
源（EXPORTING）属本集群是否（meta 命中）本地读写（切流前源服务）
源（EXPORTING）属本集群是是（meta NotFound）MIGRATED_ROUTE+目标地址 → 客户端重定向
目标（IMPORTING）不属本集群是—放行本地处理（承接迁移写 / 切流后请求）
任意不属本集群否—WRONG_ROUTE → 客户端纠正路由
目标（切流后 IN_SERVICE）属本集群——本地读写（迁移完成，目标常态服务）
为什么不断流 ① 切流是分片级原子事务，任一时刻分片只有一个权威集群；② 切流前源服务、切流后目标服务，中间无空窗；③ 落到"旧集群"的残留请求被 MIGRATED_ROUTE 一跳重定向到目标；④ 客户端/服务端路由错位被版本栅栏兜底重试。四者叠加 → 迁移分片的读写全程可服务、结果强一致。

11可用性与限流

  • 后台低优先级迁移：MigrationManager 使用独立线程池，迁移与前台请求隔离；引入可配置的批大小/速率限流（如每秒 MigrateBatch 条数），避免抢占前台 IO。
  • 小步分批：ScanTask 已按 kScanMaxBatch=100 分批扫描，天然增量、可暂停/续传。MigrationManager.cpp:42-70
  • 并发控制：Rebalancer 限制全局并发迁移任务数，优先保证在迁移集群的前台 SLA。
  • 灰度切流：切流以分片为最小单位逐个/逐批提交，单次影响面小；失败只影响该分片且可回滚。
  • 可观测性：复用 reportMigration 进度上报 + Prometheus 指标（迁移 lag、剩余分片数、重定向率、每集群分片数）供运维决策与扩缩容触发。

13风险与权衡

议题权衡与选择
迁移期写放大P2 增量转发使迁移中分片的写多发一份到目标。通过限流、仅对迁移中分片开启、lag 收敛后尽快切流来压缩窗口；分片总数固定意味着单次迁移集合有界，可控。
迁移粒度=分片分片是迁移最小单位，若单个分片数据特别大，其迁移耗时较长。因 4096 分片粒度固定且较细（每分片约总量的 1/4096），单分片体量通常可接受；扫描已按 100 条分批、可续传。
并发迁移与路由缓存多分片同时迁移时，客户端可能持有部分过期映射。路由版本栅栏 + MIGRATED_ROUTE 保证任何错位都能一跳纠正，代价是迁移窗口内少量重试。
迷你事务键定位RMSTRX 迷你事务的键被硬编码到固定分片 RMSTRX_SHARD_IDX。该分片若被重划分到新集群，需保证切流前后事务键的一致定位（沿用同一 shardId→cluster 路由即可，无特殊处理）。ObjectStore.h:47-48
缩容摘除时机必须"先迁空、路由全部刷新、无残留请求"后才停机下线集群，否则残留请求会命中已停机节点。以 OUT_OF_SERVICE 状态过渡并等待 routeVersion 收敛。
与开源对比模型等价于 Redis Cluster 固定槽 + 槽→节点重映射：分片数不变、只搬归属、客户端重定向。相比 TiKV/Vitess 的 range split 更简单，恰好匹配"只改集群数"的需求。
小结 本方案把 Goblin 从"静态 M 集群"演进为"集群数可 M→N 弹性伸缩"的系统，分片总数固定为 4096、每个分片始终只属于一个集群。落地重点是打通既有迁移脚手架（补 MigrateBatch 接收端、启用 onboardCluster 重平衡、实现 removeCluster、支持并发多任务）。数据迁移用"复制→增量追平→原子切流→清理"四阶段保证不丢不重；迁移期读写用"路由版本栅栏 + EXPORTING/IMPORTING 逐分片判定 + MIGRATED_ROUTE 重定向"保证全程不断流。所有一致性保障均建立在 Goblin 已有的 Raft、路由栅栏与 event-sourcing 之上。
