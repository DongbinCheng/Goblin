Background

Goblin already supports Raft Reconfiguration to resize a single Raft cluster. This design adds Dynamic Sharding: scaling the number of Goblin OS clusters and moving data between them while the system stays online.

Scope of this document is data migration between clusters only. Cluster build / destroy is out of scope.

OneOM (route brain) Source OS cluster (EXPORTING) Target OS cluster (IMPORTING) Client

Requirements at a Glance

Functional

  • Increase / decrease shard count for one Goblin OS.
  • No data loss during migration.
  • Clients always read the latest value/version of a key — whether it sits on the source or the target.

Non-functional

  • Migration must not hurt availability of OM or OS clusters.
  • Tolerate leader change / rollout: every state change is persisted in the Raft log and replayed into the state machine, so migration resumes from its breakpoint.

System Topology

Migration Lifecycle (bird's-eye)

1 · OM Task Driver — per-shard orchestration

AddCluster / RemoveCluster (scoped by app_env) recomputes the consistent-hashing ring and records a MigrationTask into the Raft log & state machine. A background consumer in OM then processes the task shard by shard:

  1. Generate a ShardMigration command in OM, persist to Raft log.
  2. After it applies, send StartMigration RPC to both source & target OS clusters.
  3. When OM receives OnMigration from the source, it generates a FinishShardMigration command.
  4. After that applies, OM sends FinishMigration (then later EndMigration with the bumped route) to source & target.

Because every step is a committed command, a leader change / rollout in OM does not lose progress — the task resumes at its breakpoint.

2 · Labeling Shards to be Migrated

When source/target OS clusters receive StartMigration, each generates a ShardMigration command persisted into its own Raft log & state machine, labeling the shard EXPORTING (source) or IMPORTING (target).

Once committed, a consumer thread in the OS generates many MigrationCommands in the background to move all keys of that shard from the source — one by one, or batch by batch.

3 · Key Move — Start & Finish commands

The move of each key batch on the source cluster is split into two persisted commands. Note the two apply layers: the in-memory state machine and the durable EAL (RocksDB).

4 · Source-anchored Reads & Writes

During a shard migration the OM route version is not bumped yet, so clients keep sending shard-S keys to the source cluster:

  • Key still on source → source handles it normally.
  • Key already moved → reply MIGRATED_ROUTE; client retries against the target cluster.
  • The target accepts requests for keys in an IMPORTING shard even though route info doesn't yet assign that shard to it.
Before replying MIGRATED_ROUTE, the server must wait until appliedIndex ≥ the max version it saw in CPL. This guarantees the "not found → migrated" decision is based on fully-applied state, not just committed state.

5 · Bump Route Version When a Shard is Done

  1. Source finishes the shard → sends OnMigration to OM.
  2. OM bumps the route version and sends the new route to source & target via EndMigration.
  3. Both clusters remove the EXPORTING / IMPORTING label for that shard.
  4. Clients refresh route info and now send migrated keys straight to the target cluster.

Repeat for many shards

OM can run concurrent shard migrations across different OS clusters, but only one shard at a time per cluster to protect serving latency. When one shard finishes, OM triggers the next.

Exposed migration status

OM exposes a gRPC status call (used by admin / erdapel) reporting how many shards have been migrated so far.

Request Handling Matrix (shard in EXPORTING)

If a cluster owns any EXPORTING shard, requests to that shard are handled specially: every request must first check whether the key still exists locally, and the reply depends on the version applied in CPL (not merely committed), because a committed index cannot guarantee the key was persisted on the target.

CommandKey existsKey not exist
Read wait readVersion committed → reply OK wait read/deleted version applied → reply MIGRATED_ROUTE → client retries target
Write / Delete wait writeVersion committed → reply OK wait writeVersion applied → reply MIGRATED_ROUTE → client retries target
Trans All exist / all not-exist → same as above. Partially exist → retry (Redis-style TRYAGAIN).
Follower read open question (from the design): Can follower reads be redirected to a target-cluster follower? A key that is being migrated and still exists may appear "not existing" on a target follower that hasn't yet applied the batch — a correctness hazard.

End-to-End Sequence (single shard)

⚠️ Risks & Concerns

The design is careful about durability and leader-change tolerance. The items below are areas worth pinning down before/while implementing.

R1 · Follower reads on the target can return stale "not found" High

The design itself flags this. If follower reads are redirected to a target follower, a key that does exist (already migrated, but that follower hasn't applied the batch) can look "not existing," violating the "always see latest value" requirement. Recommend: disallow follower reads for IMPORTING/EXPORTING shards, or gate them on the follower's applied index ≥ the batch's migration index.

R2 · MigrateBatch idempotency & the ABA hazard High

Correctness hinges entirely on the target's de-duplication. Consider: source moves key k=v1, target applies it, then a new client write k=v2 lands on the target (IMPORTING accepts it); a delayed retry of the original MigrateBatch could overwrite v2 back to v1. De-dup "already executed" is not enough — the dedup key must be per-batch/per-version and the handler must reject stale-version writes, not just duplicate ones. This needs an explicit spec (e.g. version-conditioned upsert).

R3 · Committed vs. applied divergence between leader and followers Medium

Reads on an existing key reply after "committed", but writes/deletes on a not-exist key reply after "applied". The rationale is sound, yet mixing the two thresholds for the same shard is subtle. A leader that crashes between "committed" and "applied" could let a new leader answer differently. Recommend documenting the exact wait condition (the appliedIndex ≥ maxVersion in CPL rule) uniformly and adding tests around the crash window.

R4 · Window where a key exists on neither / both clusters Medium

Between "delete on source (EAL)" and "route bump", the key lives only on the target while the shard still routes to source. This is handled by MIGRATED_ROUTE + target accepting IMPORTING, but it depends on the client honoring the redirect promptly. A client with a very stale route or a redirect loop (source says "migrated", target says SERVER_ROUTE_OUT_OF_DATE) could bounce. Worth a bounded retry / loop-breaker.

R5 · Blocking EAL apply can stall the state machine Medium

MigrateBatch runs inside a blocking EAL apply and waits for the target's success. If the target is slow or partitioned, the source's apply pipeline stalls — which can back up unrelated writes and hurt availability (a non-functional requirement). Recommend timeouts + async continuation (persist Task, release apply thread, resume on callback) rather than blocking the apply loop on a network RPC.

R6 · Marking DELETE in memory before EAL durability Medium

MigrationKeysStartCommand marks keys DELETE in the in-memory machine first; durability/RPC happen in EAL. If the two layers can be observed independently (e.g. a read served from memory), a key could appear deleted before it is safely on the target. Confirm reads always respect the EAL/applied gate so the in-memory DELETE isn't visible prematurely.

R7 · Route bump is per-shard → many version bumps & client refresh churn Low

Migrating a large cluster moves many shards, each bumping the route version and forcing clients to refresh + retry (CLIENT_ROUTE_OUT_OF_DATE). Under high fan-out this is extra OM load and client-side latency spikes. Consider batching label removals or coalescing version bumps where safe.

R8 · Concurrency scope & ordering guarantees Low

"One shard at a time per cluster" protects latency, but a cluster can be both a source (for shard A) and a target (for shard B) simultaneously across different tasks. Ensure the "any EXPORTING shard → special handling" check, label bookkeeping, and status reporting compose correctly when a cluster plays both roles. Also define behavior for RemoveCluster where the target set may itself be shrinking.

R9 · Failure / rollback path is underspecified Low

The happy path is well covered, but what happens if a target cluster is permanently unhealthy mid-shard, or an operator aborts? There is no described way to cancel a MigrationTask, un-label shards, or reconcile half-moved keys. A documented abort/rollback command would improve operability.

Summary

Goblin Dynamic Sharding moves data shard by shard under OM orchestration, keeping traffic on the source cluster until each shard is fully copied and durably confirmed on the target, then bumping the route version so clients flip to the target. Durability comes from the store-then-delete ordering inside blocking EAL applies, and resilience comes from persisting every state change as a Raft command so migration resumes after leader changes.

The strongest areas to harden before production are: target-side idempotency/versioning (R2), follower-read correctness (R1), and avoiding blocking the apply loop on network RPC (R5).
