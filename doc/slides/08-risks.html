8⚠️ Risks & Concerns to Review

The design is solid and the persistence-everywhere principle is the right backbone. Below are concrete points that deserve a closer look before implementation.

R1. Missing-vs-migrated key — resolved by design (Redis-style) Resolved

Per the design decision, there is intentionally no per-key "moved" marker, matching Redis slot migration. In an EXPORTING shard, any absent key → MIGRATED_ROUTE → retry on target. Accepted trade-off to be aware of: a GET for a key that is genuinely absent everywhere (deleted or never existed) costs one extra round-trip (source says redirect, target returns not-found). The target is the authoritative "not found" during migration, so there is no infinite ping-pong as long as the target does not itself redirect back (it owns the IMPORTING shard and answers definitively).

R2. New keys during EXPORTING — resolved by design Resolved

A brand-new key created in an EXPORTING shard does not exist at source, so the same rule applies: source replies MIGRATED_ROUTE and the client writes it directly to the target. New inserts therefore land on the target from the start and are never stranded on the source after the route flips — no special new-key path needed. Confirmed: both writes and reads of an absent key in an EXPORTING shard return MIGRATED_ROUTE — not just reads — so new writes are steered to the target rather than recreated on a soon-to-be-emptied source.

R3. Cross-cluster atomicity — handled by persisted command replay Resolved

The MigrationCommand is persisted in the source's Raft log, so it is replayed-until-complete rather than truly atomic. If the source crashes after the target commits but before the local delete, recovery re-applies the same command: it re-sends MigrateBatch (idempotent on the target) and re-runs the local delete. The command only retires once both the target ack and the local delete have succeeded, so the transient "key in both places" state is always reconciled to target-only. During the whole window reads stay anchored to the source, so clients never observe the duplicate.

Two invariants this relies on — keep them explicit in the implementation:

  • Target idempotency: a replayed MigrateBatch must not overwrite a value the target has legitimately updated later. While the shard is IMPORTING and the route hasn't flipped, the target hasn't taken independent writes yet, so a re-import is safe; pair with a per-command monotonic id (see R7) to be defensive once labels/route change.
  • Delete is part of the same replayable command: the local delete must be driven by the persisted command (not a side effect), so a crash before the delete is always retried on recovery.

R4. EAL blocking on cross-cluster ack — resolved (replies don't wait on EAL) Resolved

The MigrationCommand may genuinely block EAL until it gets the target response, but Raft does not rely on EAL to reply to clients for non-related traffic. Once an entry is persisted into the Raft log by a majority of pods it is committed and can be replied to the client; the apply (EAL) step is independent of that acknowledgement path. So even if EAL stalls on a slow, partitioned, or leader-changing target, unrelated reads/writes keep being committed and answered — EAL lag does not affect availability. The blocking is local bookkeeping for the in-flight migration, not a client-facing stall.

R5. removeCluster data-loss ordering — resolved (persisted in OM Raft log) Resolved

All addCluster/removeCluster operations are persisted to OM's Raft log. Because the cluster-membership change is itself a committed log entry, the destroy path is naturally sequenced after — and gated on — the persisted migration progress ("all shards fully migrated & EndMigration acked"). The gate and the teardown are both durable, so a leader change cannot tear down a cluster whose EXPORTING shards have not finished, and no keys are lost.

R6. MIGRATED_ROUTE retry — resolved (insert-if-absent makes retries safe) Resolved

The target accepts the redirected request under its IMPORTING label, bypassing the normal route-version rejection, so a MIGRATED_ROUTE retry lands. Combined with the insert-if-absent rule for MigrateBatch (see R7), repeated retries converge rather than loop: whoever writes the key first wins, and a later migrated copy never clobbers it.

R7. Idempotency for MigrateBatch — resolved (write only if key does not exist) Resolved

MigrateBatch writes a key-value on the target only if the key does not already exist. This single rule makes the batch idempotent without a separate sequence id: if the key is already present it is not overwritten, because that existing value is either

  • a copy written by a previous (retried) MigrateBatch for the same key — re-applying would be a no-op anyway; or
  • a newer value written by a client. This can happen because the MigrationCommand releases its per-key lock once it passes CPL, while EAL may have a large lag. During that window a client write for the same key finds it absent in the CPL state machine and is accepted — so the client's value is the authoritative, newer one and must not be overwritten by the lagging migrated value.

Either way, "skip if present" guarantees a retried or delayed MigrateBatch never replaces newer data with stale migrated data.

R8. Single OM leader as migration driver — resolved (idempotent task + OS-side rejection) Resolved

Leader churn is not a correctness problem on its own: a ShardMigrationTask may be triggered by leader A and have its OnMigration result received by leader B, and the migration still completes correctly because all task state lives in OM's Raft log rather than in the leader's memory. The one real hazard is double-driving — two attempts (across a leader change) issuing the task for the same shard. This is closed on both sides:

  • Idempotent ShardMigrationTask: the task carries a stable per-shard identity, so re-issuing it for a shard already in flight is a no-op rather than a second, conflicting migration.
  • OS-side rejection: the OS rejects a ShardMigrationTask for a shard that already has an active migration (already labeled EXPORTING/IMPORTING with a live ShardMigration task). The OS-side task state remains the source of truth for progress, so a new leader's re-drive reconciles against it instead of starting a duplicate.

Together these make driving the task at-least-once safe: whether the trigger and the result land on the same leader or different leaders, exactly one migration runs per shard.

R9. Consistency model during the window — resolved Resolved

The only way the source and a migrating key can diverge is the EAL-lag window above: after the MigrationCommand passes CPL and drops the lock, a client may write the key before EAL applies the migration. The insert-if-absent rule on the target resolves this deterministically — the first writer of the key wins and the migrated value defers to any value already present. Reads of an EXPORTING-shard key stay anchored to the source (absent → MIGRATED_ROUTE → target), so clients always observe the latest value and never a stale migrated copy.

R10. Cross-cluster CPL/EAL skew — resolved (version-aware reads: commit-wait for hits, commit+apply-wait for redirect) Resolved

Goblin's CPL (in-memory state machine) runs ahead of EAL (RocksDB apply). A migrated key is deleted in source CPL the moment its MigrationCommand passes CPL, but the local delete is not yet persisted in RocksDB, and EAL may not have reached it. Naively, a read could miss the key in source CPL, get MIGRATED_ROUTE, retry the target, and find it not yet imported there either — a brief "nowhere" window. Resolved by making source reads version-aware, exploiting that export order is always MigrateBatch (target acks) → local delete:

  • Normal hit → wait for commit only. The value the read sees in CPL is replied once that version is committed by a Raft majority — i.e. the data is durable. Cheap, no apply-wait.
  • Absent → MIGRATED_ROUTE → wait for commit and EAL apply. The redirect is held until EAL has applied up to the read's commit index, so every delete the source could redirect for is persisted, which means each such key was already MigrateBatch-acked at the target. The redirect therefore only leaves once the key is guaranteed present at the target — the nowhere window collapses by construction, with no per-key tombstone and no extra storage.

The apply-wait is bounded by "EAL caught up to current commit index," so genuinely-absent keys and non-migrating shards pay at most one extra round-trip, not a migration-long stall. Builds on R3 (delete is part of the persisted command, so apply truly implies target-acked) and R7 (insert-if-absent keeps the import idempotent).
