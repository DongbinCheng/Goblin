✓Summary

Dynamic sharding moves shards one-at-a-time per cluster, keeps reads/writes anchored to the source until a key actually moves, and flips the route version only once a shard is fully migrated. Persisting every state change into Raft is what makes it resumable across leader changes. Following the Redis-style decision, there is no per-key "moved" marker: absence at the source always means "redirect to target" (MIGRATED_ROUTE), which cleanly handles both migrated and brand-new keys (R1, R2 resolved). Cross-cluster atomicity (R3) is handled by replaying the persisted MigrationCommand until both the target ack and the local delete succeed, reconciling any crash-window duplicate to target-only. EAL blocking does not hurt availability (R4): clients are replied once entries are committed to the Raft log by a majority, independent of EAL apply. Cluster membership changes are persisted to OM's Raft log so teardown is safely sequenced (R5), and MigrateBatch is insert-if-absent — it writes a key only if absent — which makes it idempotent and lets a newer client value written during EAL lag win over a lagging migrated copy (R6, R7, R9 resolved). Finally, leader churn on the OM migration driver is safe (R8 resolved): a ShardMigrationTask can be triggered by one leader and completed under another because all task state is in OM's Raft log, and double-driving is prevented by making the task idempotent and having the OS reject a second ShardMigrationTask for a shard already migrating. The cross-cluster CPL/EAL skew is closed (R10 resolved) by version-aware reads: a hit waits only for commit, but an absent-key MIGRATED_ROUTE waits for commit and EAL apply, so the source only redirects once every migrated delete is persisted and the key is guaranteed present at the target — no per-key tombstone, no extra storage.
