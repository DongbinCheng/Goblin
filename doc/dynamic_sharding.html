🧩 Goblin Dynamic Sharding

How a Goblin OS (Object Store) cluster set scales horizontally by migrating shards between clusters — with zero data loss and uninterrupted availability. This page visualizes the design and flags design risks worth a second look.

1The Big Picture

Vertical scaling of a Goblin component = Raft Reconfiguration (change cluster size). Horizontal scaling = Dynamic Sharding (this design): move some of the 4096 shards from one OS cluster to another while traffic keeps flowing.

OneOM — route authority Source OS cluster Target OS cluster Client

OneOM

Single route authority per app_env. Holds RouteInfo and migration task state in its Raft state machine. Bumps route version.

OS clusters

Each is its own Raft group storing a slice of the 4096 shards. Source exports, target imports.

Clients

Fetch RouteInfo from OM, cache it with a version, and are corrected via route-out-of-date rejections.

2Route Info & Version Reconciliation

Every key → one of 4096 shards by consistent hashing. RouteInfo maps shardId → clusterId plus the UDNS of each partition. A monotonically increasing route version keeps everyone in sync.

OM bumps the version when pods are added/removed in a partition (vertical) or when a cluster is added/removed (horizontal). An OS leader refreshes RouteInfo in onBecomeLeader before serving traffic.

3End-to-End Migration Flow

A single shard's journey from source to target. Every step is persisted in a Raft log, so a leader change or rollout simply resumes from the last committed point.

  1. Admin-driven route change. addCluster/removeCluster recomputes the ring; OM records the migration task into its Raft log & state machine so it survives leader change.
  2. Per-shard task setup. The OM migration-task consumer (leader only) sends StartMigration to source & target; each persists a ShardMigration task and labels the shard EXPORTING / IMPORTING.
  3. Background commands. Once the ShardMigration task commits, the source generates many MigrationCommands to move every key.
  4. Atomic move. Each command sends a MigrateBatch to target, waits for ack, then deletes local data — atomically under a per-key lock.
  5. Finish & version bump. Source sends OnMigration to OM; OM bumps the version and sends EndMigration with the new route; both clusters drop the IMPORTING/EXPORTING labels.

4Per-Shard State Machine

The route version is only bumped at the final transition, so clients keep pointing at the source for the whole migration window and never see a half-moved shard through the route table.

5Source-Anchored Reads/Writes

During migration, clients (still on old route) send requests for the shard to the source. The decision tree:

The target accepts requests for keys whose shard is labeled IMPORTING, even though, per the old route, those keys don't yet officially belong to it. That's what makes the MIGRATED_ROUTE retry land successfully.

Design decision: no per-key "moved" marker (Redis-style)

There is deliberately no key-level migration label — exactly like Redis slot migration. The rule for an EXPORTING shard is simply: if the key exists at source, serve it; if not, reply MIGRATED_ROUTE and let the client retry on target. This single rule covers two cases at once:

  • Already-migrated key — deleted from source after its batch moved → absent → redirect to target (where it now lives).
  • Brand-new key in the shard (created during EXPORTING) — never existed at source → absent → redirect to target, so new inserts land directly on the target. No risk of being stranded on source after the route flips.

Because absence always means "go ask target," source and target together always present a complete, consistent view of the shard without tracking individual key state.

6The Atomic MigrationCommand

What it does

  1. Acquire per-key read/write lock (blocks concurrent ops on K).
  2. Send MigrateBatch to target; block EAL until target acks the data is stored.
  3. Delete local copy of K.
  4. Release lock. Command is persisted, so it resumes after restart.

Why it's safe

  • Export + delete are atomic for a key — no window where K exists in both or neither place servicing writes.
  • Persisted in the Raft log → survives leader change / rollout.
  • Idempotent — a re-sent MigrateBatch after a lost response must not corrupt state.
  • Target accepts MigrateBatch under its old route, keyed by IMPORTING label.

8⚠️ Risks & Concerns to Review

The design is solid and the persistence-everywhere principle is the right backbone. Below are concrete points that deserve a closer look before implementation.

R1. Missing-vs-migrated key — resolved by design (Redis-style) Resolved

Per the design decision, there is intentionally no per-key "moved" marker, matching Redis slot migration. In an EXPORTING shard, any absent key → MIGRATED_ROUTE → retry on target. Accepted trade-off to be aware of: a GET for a key that is genuinely absent everywhere (deleted or never existed) costs one extra round-trip (source says redirect, target returns not-found). The target is the authoritative "not found" during migration, so there is no infinite ping-pong as long as the target does not itself redirect back (it owns the IMPORTING shard and answers definitively).

R2. New keys during EXPORTING — resolved by design Resolved

A brand-new key created in an EXPORTING shard does not exist at source, so the same rule applies: source replies MIGRATED_ROUTE and the client writes it directly to the target. New inserts therefore land on the target from the start and are never stranded on the source after the route flips — no special new-key path needed. (Worth confirming in implementation: the source must reply MIGRATED_ROUTE for writes of absent keys too, not just reads, so new writes are steered to the target rather than recreated on a soon-to-be-emptied source.)

R3. Cross-cluster atomicity — handled by persisted command replay Resolved

The MigrationCommand is persisted in the source's Raft log, so it is replayed-until-complete rather than truly atomic. If the source crashes after the target commits but before the local delete, recovery re-applies the same command: it re-sends MigrateBatch (idempotent on the target) and re-runs the local delete. The command only retires once both the target ack and the local delete have succeeded, so the transient "key in both places" state is always reconciled to target-only. During the whole window reads stay anchored to the source, so clients never observe the duplicate.

Two invariants this relies on — keep them explicit in the implementation:

  • Target idempotency: a replayed MigrateBatch must not overwrite a value the target has legitimately updated later. While the shard is IMPORTING and the route hasn't flipped, the target hasn't taken independent writes yet, so a re-import is safe; pair with a per-command monotonic id (see R7) to be defensive once labels/route change.
  • Delete is part of the same replayable command: the local delete must be driven by the persisted command (not a side effect), so a crash before the delete is always retried on recovery.

R4. EAL blocking on cross-cluster ack Medium

MigrationCommand "blocks EAL until it gets the target response." If the target is slow, partitioned, or its leader is changing, the source apply loop stalls — directly contradicting the "no availability impact" non-functional requirement. Consider an async/pipelined apply with a pending-ack state rather than blocking the state-machine apply thread.

R5. removeCluster data-loss ordering High

The doc covers data migration but says cluster destroy is out of scope. The danger is sequencing: if a cluster is torn down before all its EXPORTING shards finish and OM bumps the version, keys are lost. The destroy path must be gated on "all shards fully migrated & EndMigration acked," and that gate should itself be persisted.

R6. MIGRATED_ROUTE retry without route bump can loop Medium

Client still holds the old route, so after a MIGRATED_ROUTE retry on target, the target serves it using the IMPORTING label. But if the client's request also carries the old route version and the target enforces version checks, you could get SERVER/CLIENT_ROUTE_OUT_OF_DATE at the same time. Make sure the IMPORTING-accept path bypasses the normal version rejection, and define a retry budget to prevent loops.

R7. Idempotency keys for MigrateBatch Medium

"These commands need to be idempotent" is stated but the mechanism isn't. Without a stable command/sequence id, a retried MigrateBatch could re-import a key the target has since legitimately updated (after route flip), overwriting newer data with stale migrated data. Each command needs a monotonic id and the target must dedupe / reject stale applies.

R8. Single OM leader as migration driver Low

The task consumer runs "only in leader." On leader churn the new leader must re-derive in-flight state from the log and avoid double-driving a shard that's mid-MigrateBatch. Verify the resume logic reconciles with the OS-side ShardMigration task state (which is the real source of truth for progress).

R9. Consistency model during the window Medium

The "clients always see the latest value" guarantee depends on every read of an EXPORTING-shard key being forced through source first. Any client with a stale-but-not-rejected route, or any direct target access for an IMPORTING key that was concurrently written on source, could read stale. Worth a formal statement of the linearizability boundary for keys mid-migration.

✓Summary

Dynamic sharding moves shards one-at-a-time per cluster, keeps reads/writes anchored to the source until a key actually moves, and flips the route version only once a shard is fully migrated. Persisting every state change into Raft is what makes it resumable across leader changes. Following the Redis-style decision, there is no per-key "moved" marker: absence at the source always means "redirect to target" (MIGRATED_ROUTE), which cleanly handles both migrated and brand-new keys (R1, R2 resolved). Cross-cluster atomicity (R3) is handled by replaying the persisted MigrationCommand until both the target ack and the local delete succeed, reconciling any crash-window duplicate to target-only. The main thing still worth hardening is EAL blocking on remote acks (R4), backed by per-command idempotency ids (R7).
