Goblin Dynamic Sharding — v2 Target Design

An online (live-traffic) shard-migration design for the Object Store, modelled on Redis Cluster slot migration. Grounded in the code currently in this repository.

TL;DR Redis model Requirements 1 · Route change 2 · Migration task 3 · Shard labels 4 · Client redirect 5 · Migrate command End-to-end Proto / API Work plan

TL;DR

The key space is split into 4096 fixed shards (hash(key) & (2^12-1)). The Object Manager (OM) is a Raft control plane that owns a consistent-hash ring mapping shard → cluster and publishes it as a versioned RouteInfo. Each Object Store (OS) is itself a Raft cluster that stores the data for the shards it owns.

This v2 design makes migration online — the cluster keeps serving while data moves — using five mechanisms that mirror Redis Cluster:

  • 1Admin-driven route change. addCluster/removeCluster to the OM (one OM per app_env) recomputes the ring and bumps RouteInfo.version.
  • 2Per-shard migration tasks are delivered to the source OS clusters that must hand shards over.
  • 3Shard-level IMPORTING/EXPORTING labels (not cluster-level) track each shard's migration state — exactly Redis' per-slot MIGRATING/IMPORTING.
  • 4Source-anchored reads/writes. Clients always hit the source first; if the key is still there the source serves it, otherwise the client gets MIGRATED_ROUTE and retries the target — Redis' ASK redirection.
  • 5An atomic Migrate command holds the per-key lock across export + delete, closing the copy-then-delete race — Redis' atomic MIGRATE.

How Redis Cluster does it (reference model)

Redis Cluster moves data one slot at a time while staying available. The pieces we borrow:

Redis conceptWhat it doesGoblin equivalent in this design
CLUSTER SETSLOT <slot> MIGRATING <dst> (on source)
... IMPORTING <src> (on target)		 Marks a single slot as leaving / arriving. Per-slot, not per-node. Per-shard EXPORTING/IMPORTING label (req 3).
MIGRATE command Atomically DUMP + RESTORE on target + DEL on source for a key (or batch). New Migrate command holding the key lock across export+delete (req 5).
ASK redirection Transient, per-key: "this key already moved, ask the target this once." Route is not yet changed. MIGRATED_ROUTE with routeHint (req 4).
MOVED redirection Stable: "this slot now belongs to another node, update your map." WRONG_ROUTE / CLIENT_ROUTE_OUT_OF_DATE → refresh RouteInfo from OM.
ASKING flag Target accepts a key for an importing slot only if the client first sent ASKING. Target accepts keys for shards it is IMPORTING (the migration-set check).
The single most important borrow: in Redis the source remains the source of truth for a migrating slot until the slot is fully moved and the route is flipped. Clients are anchored to the source and only bounce to the target per-key via ASK. Goblin already encodes this with MIGRATED_ROUTE; v2 makes it correct and complete.

Component architecture

1 · Admin-driven route change at the OM

An operator adds or removes capacity by calling the OM (one OM owns the cluster-set for an app_env):

  1. addCluster. OM assigns a cluster id, inserts it into the consistent-hash ring, and recomputes which shards each cluster owns. The set of shards that change owner becomes the migration plan.
    server/src/object-manager/module/ClusterSetManager.cpp:395-437 (onboardCluster), server/src/object-manager/route/HashRing.h
  2. removeCluster (scale-in). Symmetric: the leaving cluster's shards are reassigned to the remaining clusters; those become migrations out of the leaving cluster. (Today removeCluster is a stub.)
  3. Bump RouteInfo.version. Partition/placement changes increment the version so every OS and client can detect staleness.
    protocols/common.proto:78-82 (RouteInfo.version), ClusterSetManager.cpp:328-377 (fillRouteInfo)
Two-phase route, Redis-style. The new ownership must not take effect for clients the instant the ring is recomputed — otherwise clients would route to a target that has no data yet. As in Redis (SETSLOT on src/dst first, SETSLOT <slot> NODE last), the OM should publish the final ownership flip only when a shard's migration completes:
  • Phase A (start): publish the migration task + shard labels; RouteInfo ownership for migrating shards still points at the source. Clients keep hitting the source.
  • Phase B (commit, per shard): when a shard is fully migrated, OM flips that shard's owner to the target and bumps RouteInfo.version. Clients lazily refresh on the next version mismatch.

Recommended hybrid (matches current code):
  1. OM pushes StartMigration(task, RouteInfo) to the source OS leader, and an analogous StartMigration(IMPORTING) to the target OS leader, so both sides arm their shard labels.
  2. Source OS runs the migrate pipeline and pushes progress back via OnMigration (RUNNING … SUCCEEDED).
  3. On SUCCEEDED, OM commits the route flip (Phase B) and pushes EndMigration(newRouteInfo) to both sides.
  4. Pull as a safety net: the OS startup handshake already pulls the latest RouteInfo from OM, so a crashed/restarted OS re-discovers an in-flight task. Keep this as the recovery path.

3 · Shard-level vs cluster-level labels — choose shard-level

Decision: IMPORTING/EXPORTING must be tracked per shard, not per cluster. This is exactly Redis' per-slot model and it is necessary for availability: a cluster typically owns thousands of shards and only a handful move at a time — the other shards must keep serving as IN_SERVICE.

What exists today

EnumGranularityUsed on the request path?
Cluster.ClusterStatus — EXPORTING/IMPORTINGClusterYes — preExecute branches on whole-cluster status
Migration.MigrationShardStatus — SCANNING/EXPORTING/MIGRATEDShardNo — only carried in progress reports
protocols/common.proto:127-133 (cluster-level), :97-104 (shard-level), ObjectStore.cpp:130-185 (preExecute reads cluster status)
Problem with the current cluster-level label: when a cluster is flagged EXPORTING, the preExecute loop applies migration logic to every key, even keys whose shard is not part of the task. With many shards per cluster that needlessly funnels unrelated traffic through the migration path. The in-loop checkIfInMigrationShards(shardId) guard narrows behaviour, but the authoritative state still lives at cluster granularity.

Target model

  • Promote the label to a per-shard map on each OS: shardId → {IN_SERVICE | EXPORTING | IMPORTING}, persisted via Raft alongside the migration task.
  • Cluster status becomes a derived aggregate for observability only: a cluster is "migrating" iff any shard is EXPORTING/IMPORTING; it never gates per-key routing by itself.
  • preExecute consults the shard's label for the key, mirroring Redis checking the slot's MIGRATING/IMPORTING flag.

Target side (IMPORTING): the target accepts a read/write for a shard it is importing (the migration-set check) — equivalent to Redis requiring the ASKING flag before serving an importing slot. A client redirected by MIGRATED_ROUTE is, in effect, "asking."
ObjectStore.cpp:160-166 (IMPORTING accepts migrating shard)

The correctness gap this design must close

Today "already migrated" is inferred purely from physical absence (readMeta returns NotFound), because deleteKV is a hard RocksDB delete with no per-shard "sealed" marker. That cannot distinguish migrated from never-existed (both redirect to the target, which is acceptable), but more importantly it cannot stop a new write from re-creating an already-exported key on the source, nor guarantee the export of value v1 is ordered before a redirected write of v2 on the target. Because writeKV is blind last-writer-wins and import restores the source's (older) version, a late-arriving import can silently clobber a newer live write.
RocksDBKVStore.cpp:290-308 (blind writeKV), :374-388 (hard deleteKV), CommandProcessor.cpp:264-293 + VersionStore.cpp:24-37 (import preserves source version)

Requirement 5 (the atomic Migrate command + per-key lock) is precisely the fix.

5 · The atomic Migrate command (per-key lock across export + delete)

Model this on Redis' atomic MIGRATE: for one key (or a batch within a shard) the source performs export-to-target then delete-locally as a single command that holds the key's exclusive lock for the whole duration. Any concurrent operation on the same key serializes behind that lock, so it observes either "pre-migration on source" or "post-migration → MIGRATED_ROUTE", never a torn intermediate.

Reuse the existing lock machinery

Goblin already has per-key exclusive/shared locking used by writes, and the current import command already takes an exclusive lock. The Migrate command extends the lock's scope to cover export and delete:

store/KVStore.h:66-83 (lock/unlock API), KVImportCommand.cpp:31-34 + :76-86 (exclusive lock in prepare, unlock in finish)

Ordering & idempotency rules

  • Export before delete, delete only on success. The source deletes locally only after the target confirms the import is committed (target Raft). If the target ack is lost, retry the export — import is idempotent because it is keyed and version-preserving.
  • Version-monotone import. Import keeps the source's original version so a client that read version v can still CAS on the target. Combined with the lock, a live write that beats the migrate either (a) happens entirely before the lock → its newer value is what gets exported, or (b) blocks until after delete → it is redirected to the target and applied there with a higher version. No regression either way.
    CommandProcessor.cpp:264-293 (expectedVersion = importedVersion)
  • Seal-on-export. While the key is locked/migrating the source must refuse to re-create it via a normal write; such writes are redirected (MIGRATED_ROUTE) rather than served. This is the per-shard "sealed" guarantee that pure presence-checking lacks today.
Granularity tradeoff. Locking one key at a time is simplest and lowest-impact but chatty for huge shards. A batched Migrate (lock a small key-range / scan batch, export the batch, delete the batch, unlock) amortizes the round-trips — analogous to Redis MIGRATE ... KEYS k1 k2 …. Keep batches small so unrelated keys in the shard stay available.

End-to-end flow (scale-out: add cluster B)

  1. 1Admin → OM addCluster(B). Ring recomputed; shards S move A→B. OM creates a MigrationTask(A→B, S), marks those shards EXPORTING(A)/IMPORTING(B), bumps RouteInfo.version but keeps ownership of S on A (Phase A).
  2. 2OM → StartMigration to A (source) and B (target). Both arm per-shard labels for S.
  3. 3A runs the Migrate pipeline shard-by-shard, key/batch at a time, each under the per-key lock: export to B → B commits via Raft → A deletes locally.
  4. 4Live traffic stays available. Clients hit A; present keys served by A, migrated keys → MIGRATED_ROUTE → retry B; B accepts them (IMPORTING).
  5. 5A → OM OnMigration progress until shard S is MIGRATED (SUCCEEDED).
  6. 6OM commits Phase B: flip ownership of S to B, bump RouteInfo.version, push EndMigration(newRouteInfo) to A and B; both clear the shard labels (B→IN_SERVICE owner).
  7. 7Clients notice the version bump on their next request and lazily refresh, now routing S straight to B (MOVED-style).
