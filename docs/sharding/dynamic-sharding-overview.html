Goblin Sharding & Dynamic Re-sharding

How 4096 shards map to clusters, how mapping shifts when clusters are added/removed, and how much data migrates.

1. The big picture: 4096 fixed shards

Every key in Goblin is hashed into one of 4096 fixed shards. Shards are the unit of placement — clusters come and go, but the shard count never changes.

key ──simpleHash──> shardId = hash & (2^12 - 1)   // 0 .. 4095   (4096 shards)
shardId ─────────> columnFamily = shardId & ((1<<factor)-1)   // local sub-split
  • OM (Object Manager) owns the shard → cluster map, built by a consistent-hash HashRing of length 4096.
  • OS (Object Store) routes each key with keyToShardId and picks a local column family from the shard id.
Source: object-store/ObjectStore.h (keyToShardId :130, columnFamily :78), route/HashRing.h (RING_LENGTH=4096 :52), protocols/common.proto (Shard.DEFAULT=12).

2. How shards are divided into clusters (the ring)

Each cluster is placed at VIRTUAL_NODE_COUNT point(s) on the 0..4095 ring: point = hash(clusterId#i) % 4096 (collisions probe forward). A cluster owns every shard from its point up to the next cluster's point, wrapping around. This is classic consistent hashing.

extractShardConfig walks the ring and assigns each shard to the owning cluster; addClusterId/deleteClusterId mutate the ring.

3. What changes when you add a cluster

A new cluster inserts a point on the ring and only steals the arc between its point and the next point from a single predecessor. All other arcs stay put. With consistent hashing, going from N to N+1 clusters moves roughly 1/(N+1) of all shards.

Migration only flows from one predecessor into D (yellow). A and C are untouched.

4. What changes when you remove a cluster

deleteClusterId drops all of that cluster's points; its arcs collapse into the next surviving cluster. Only the removed cluster's shards migrate (~1/N), and they land on neighbors — no other arcs move.

5. Migration estimate

With single virtual node and even spacing, the data to migrate is just the shards crossing ownership:

TransitionShards movedFraction
3 → 4 clusters (add)≈ 4096/4 = 1024~25%
4 → 5 clusters (add)≈ 4096/5 ≈ 819~20%
N → N+1 (add)≈ 4096/(N+1)~1/(N+1)
N → N−1 (remove)≈ 4096/N~1/N

Per-shard bytes = total dataset / 4096, so migrated bytes ≈ (shards moved) × dataset/4096. More virtual nodes spread the moved shards across more sources but keep the same total fraction.

6. Current state: scaffolding only

Dynamic re-sharding is not yet wired. onboardCluster computes the shard map but the rebalance / migration-task creation is commented out (static sharding only), and MigrateBatch has no server-side CallData. The estimates above describe expected behavior once enabled.
