Goblin 动态分片 · Dynamic Sharding 设计

跨 OS 集群的按需数据迁移  |  不丢数据 · 强一致版本 · 容忍 leader 切换

OVERVIEW 为什么需要动态分片？

随着业务增长，Goblin 存储的数据量持续增加。本设计聚焦 集群之间的数据迁移（不涉及集群的创建/销毁）， 实现单个 Goblin OS 的分片规模弹性伸缩。

🎯 目标场景

  • GoblinRMS Cluster：单 shard 快照约 1.4 TB
  • FAM/FAS PU：若用 Goblin 存历史 dedupid，单快照约 1 TB

✅ 功能需求

  • 支持一个 OS 的分片数增加 / 减少
  • 迁移过程不丢任何数据
  • 客户端始终读到某 key 的最新值/版本，无论它在源还是目标集群

🛡 非功能需求

  • 迁移不影响 OM / OS 集群可用性
  • 容忍 OS/OM 的 leader 切换 / rollout，切换后可无错续跑
  • 每个操作/状态变更都持久化进 raft log 并加载到状态机

KNOWLEDGE 前置知识：路由与版本

理解迁移前，先理解 Goblin 的路由体系（谁决定一个 key 落在哪个集群）与 route version 的协商机制。

🗺 Route Info（存于 OneOM 状态机）

  • OneOM 在本地状态机保存所有 OS 的路由信息；不同集群的 routeinfo 存在不同 app_env（OM 命名空间）下。
  • 所有 key 通过一致性哈希分到 4096 个 shard，这些 shard 分布在一个/多个 OS 集群。
  • Route Info = 每个 partition 的 OS UDNS + shardId → clusterId 映射，决定 key 存到哪个集群。
  • 客户端从 OneOM 获取 routeinfo，据此知道 UDNS 与映射。

🔢 Route Version 协商

比较结果拒绝码后续动作
client < serverCLIENT_ROUTE_OUT_OF_DATE客户端向 OM 刷新路由
client > serverSERVER_ROUTE_OUT_OF_DATE服务端向 OM 刷新路由
OM 何时 bump route version？
① 增删某 OS 集群的 pod（改集群内 pod 数）；② addCluster / removeCluster（改分片数）——迁移时 bump。

OS leader 在 onBecomeLeader 时刷新 route info，然后才开始服务流量。

ARCHITECTURE 三层角色与整体数据流

OM 编排（生成迁移任务、按 shard 调度）；源/目标 OS 执行（打标签、逐 key 同步）；Client 按 route version 收敛到正确集群。

控制/RPC 数据同步 客户端交互 虚线=回调/续跑

OM · KEYPOINT 1 按 shard 迁移：OM 的编排与断点续跑

对 OneOM 执行 addCluster/removeCluster（带 app_env）会重算 ring，并把迁移任务记录进 raft log 与状态机；一个后台消费线程逐 shard处理。

🧵 OM 内的编排流程（每个 shard）

  • 1
    后台线程为该 shard 生成 ShardMigrationCommand，持久化进 raft log。
  • 2
    命令 applied 后，向源 & 目标 OS发送 StartMigration RPC。
  • 3
    收到源集群 OnMigration 后，OM 生成 FinishShardMigration Command。
  • 4
    该命令 applied 后，OM 向源 & 目标发送 FinishMigration（EndMigration）。

🔑 dedupid：幂等 + 断点续跑

在 OneOM 的 RocksDB 中，记录所有待迁移 shard_id与正在迁移的 shard_id，均以 {app_env} 为前缀。

ShardMigrationCommand 使用的 dedupid：

  • migrationin_{cluster_id}_{shard_id}
  • migrationout_{cluster_id}_{shard_id}
有了 dedupid，RPC 失败或 leader 切换时，重放 MigrationTask 可任意重试而不重复迁移。
leader 切换/重启时，OM 总是从 RocksDB 载入待处理 MigrationTask ⇒ 任务状态被追踪，可从断点继续。

OS · KEYPOINT 2 给 shard 打标签：EXPORTING / IMPORTING

源/目标 OS 收到 StartMigration 后，各自生成 ShardMigration Command 并持久化进 raft log 与状态机，把该 shard 打上标签。

🏷 两端标签

源集群 · EXPORTING 标记该 shard 正在迁出。

目标集群 · IMPORTING 标记该 shard 正在迁入。

ShardMigration Task 提交后，源 OS 内有一个消费线程在后台生成大量 KeyMigrationCommand，把源侧所有 key 逐个/逐批迁移。

🧭 标签的意义

  • EXPORTING：源集群仍是该 shard 的权威（source-anchored），负责响应/重定向。
  • IMPORTING：目标集群提前接受属于该 shard 的请求，即使按当前 route info 它还不该属于目标。
  • 标签持久化在独立的结构/列族中（内存 + RocksDB 双写），保证 leader 切换后可恢复。
标签是"迁移期临时路由覆盖层"：在 route version 尚未 bump 前，让两端协同处理同一 shard 的流量。

OS · KEYPOINT 3 单个 KeyMigration 的两阶段

迁移命令在源集群 leader生成，分两步：MigrationKeysStartCommand 与 MigrationKeysFinishCommand。

状态双写

迁移中 key 的所有状态同时存内存与 RocksDB（独立结构/列族），保证可恢复。

目标幂等

目标集群可能多次收到同一 key，直接覆盖并回成功。

新 leader 恢复

新 leader 应用完 raft log 并载入 ShardMigration Task 后，重试 MIGRATING 的 key，再继续其余 key。

KEYPOINT 4 Key Version 与 Lamport Clock

version 用于 CAS 与 Watch。跨集群同步一个 kv 时，目标集群保留原 version；这本质上是 Lamport Clock 的"取较大者再推进"。

📥 同步 = ImportCommand（一 key 一命令）

  • 源集群的 kv 同步请求在目标集群作为 ImportCommand 处理（每个 key 一条命令）。
  • 同步时 version 在目标集群被原样保留，使 CAS / Watch 语义跨集群保持一致。
因为 version 被保留，源集群在该 key 迁移后可安全地把客户端重定向到目标集群继续 CAS。

⏫ maxVersion 单调抬升

若 ImportCommand 里 key 的 version 大于目标集群的 maxVersion，则把 maxVersion 抬升到该 key 的 version。

这保证：该 key 后续在目标集群产生的新版本一定更大，version 永远单调递增，杜绝回退 / ABA。

Lamport 规则映射：目标计数器 = max(本地, 迁入version) 再前进 —— 与 Goblin 中 allocateNextVersion 抬升 mNextVersion 的逻辑一致。

KEYPOINT 5 源锚定读写（Source-anchored）

迁移进行中，OM 不 bump routeVersion，该 shard 的请求仍发往源集群。源集群按 key 的标签状态分类处理。

🔀 源集群按标签的响应逻辑

Key 状态响应
不存在于源集群MIGRATED_ROUTE 让客户端改发目标集群
存在且无标签（尚未迁移）源集群自己处理
存在且 MIGRATED同上，重定向到目标
存在且 MIGRATING见右侧：简化为 RETRY

⚠️ 为什么 MIGRATING 用 RETRY 而非等待？

若源 leader 仅等待 CPL 中出现 MIGRATED 标签就回复，一旦 MigrationKeysFinishCommand 提交前发生 leader 切换，新 leader 会重发该 key ⇒ ABA 风险。

最终设计：只要有任意 key 处于 MIGRATING，直接回 RETRY 让客户端重发；待所有 key 变为 MIGRATED，再回 MIGRATED_ROUTE。
目标集群应接受标了 IMPORTING 的 shard 的请求 —— 即使按当前 route info 该 shard 还不属于目标集群。

KEYPOINT 6 每个 shard 迁移完成后 bump route version

一个 shard 在源集群迁移完成 → 源发 OnMigration 给 OM → OM bump route version 并用 EndMigration 下发新路由。

源集群在 apply FinishMigrationCommand（由 OM 的 EndMigration 触发）时：更新 route info 以拒绝已完成 shard 的 key，并删除独立结构/列族中的 key 标签。

KEYPOINT 7 · 8 多 shard 迁移的调度 & 状态暴露

🔁 重复迁移多个 shard

  • OM 可对不同 OS 集群并发触发 shard 迁移任务。
  • 但对同一个 OS 集群不并发多个 shard 迁移，以免影响流量服务延迟。
  • 因此：某集群一个 shard 迁完后，OneOM 才对它触发下一个 shard 迁移任务。
"跨集群并发、同集群串行" —— 兼顾迁移吞吐与在线延迟。

📊 OM 暴露迁移状态

  • OneOM 需对外暴露迁移状态：当前已迁移多少 shard。
  • 该 gRPC 由 admin（erdapel）调用。
状态来源于持久化的 MigrationTask（RocksDB），与断点续跑同源，保证 leader 切换后统计仍准确。

FEATURE 单键读写删 & 多键事务

只讨论属于正在迁移 shard 的 key。核心：按 key 标签把请求收敛到唯一权威集群。

🔑 Single Key Read / Write / Delete

Key 状态行为
存在·无标签（未开始）源集群处理，等 version 提交 → OK
存在·MIGRATING回 TRY_AGAIN；客户端重试源集群直到拿到 MIGRATED_ROUTE；最终由目标处理
MIGRATED / 不存在源回 MIGRATED_ROUTE → 目标集群处理

🧩 Trans / 多键复合操作

各 key 状态组合处理方
全部相同同单键规则
部分无标签 + 部分不属于迁移 shard源集群
部分不存在 + 部分 MIGRATED目标集群
部分 MIGRATED + 部分 MIGRATINGTRY_AGAIN

FEATURE CAS · Watch · FollowerRead

🔁 CAS

迁移 key 的 version 被保留，因此源服务器在 key 迁移后可安全地把客户端重定向到目标继续做 CAS —— 版本比较结果跨集群一致。

version 保留是 CAS 跨集群正确的根基。

👁 Watch

Watch 是 client 与 server leader 间的长连接。当被 watch 的 key 迁移并被打上 MIGRATED，应通过一个事件通知客户端"该 key 已迁移"。

客户端据此改向目标集群重新建立 watch。

📖 FollowerRead

能否把 followerRead 重定向到目标集群的 follower？可以。

Follower read 不要求强一致，无论请求发往源还是目标集群都可接受。

与仓库实现印证：follower read 绕过内存 KV（含 leader 未提交脏写），直接读 RocksDB 中已提交数据 —— 因此对源/目标皆安全。

SUMMARY 容错要点与设计不变量

整套设计的正确性建立在"所有状态变更持久化 + 标签驱动的单一权威 + version 单调保留"三大支柱上。

🧱 持久化一切

  • OM：ShardMigrationCommand / FinishShardMigration 进 raft log；MigrationTask + dedupid 存 RocksDB。
  • OS：ShardMigration / MigrationKeysStart / Finish 进 raft log；key 标签内存+RocksDB 双写。

🔁 幂等 & 断点续跑

  • dedupid 让 OM 任务任意重试不重复。
  • 目标对重复 key 覆盖即成功。
  • 新 leader 载入任务后重试 MIGRATING key，续跑其余。

🎯 单一权威 & 单调版本

  • 标签 + RETRY/MIGRATED_ROUTE 保证同一 key 只被一个集群权威处理。
  • version 保留 + maxVersion 抬升 ⇒ 单调递增，防 ABA。
  • routeVersion 每完成一个 shard bump 一次。
结论：迁移期间数据不丢、客户端始终读到最新版本、OM/OS 可容忍 leader 切换并从断点无错续跑 —— 满足全部功能与非功能需求。
